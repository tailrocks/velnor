# Plan 2026-09-14: native Engine API slice 4 — container exec for run steps (GOAL 17/58)

Base: origin/main tip 51ab97a3 at fetch time. Branch: r0-engine-api-4.
Worktree: /tmp/velnor-eng4. Follows slices 1-3 (reads, lists, idempotent
lifecycle mutations).

## Problem

Slices 1-3 routed control-plane queries and maintenance-path mutations;
every run step still pays one `docker exec` subprocess plus its env-file
round trip, and run steps are the per-job hot path — the representative
job's dozens of `docker` processes are mostly steps. This slice adds the
fourth Engine-API leg: `exec_create` + `exec_start` with multiplexed
output demux over `docker/engine.rs`, applied to ONE step-execution path
(run steps in containers).

## Fix (this branch, strict scope)

Three new engine endpoints plus one typed facade route with the slice-1
contract, extended to a payload call — API first, historical CLI on ANY
API failure, taxonomy preserved, deadlines plus cancellation plus
fallible runtime plus current-thread offload reused, telemetry on
fallback:

- `exec_create(container, config)` — `POST /containers/{id}/exec`, JSON
  document mirroring the CLI leg's flags exactly (no `-i`/`-t`/`-d`/
  `--user`, same `Cmd`/`Env`/`WorkingDir`), 201 carries the id;
- `exec_stream(id)` — `POST /exec/{id}/start` (`Detach:false`,
  `Tty:false`), 200 plus the hijacked close-delimited multiplexed
  stream, demuxed incrementally (8-byte headers, stream 1/2) with the
  CLI runner's own line semantics mirrored exactly (per-stream `\n`
  split, one trailing `\r` strip, lossy UTF-8, unconditional `\n`
  terminator per emitted line, unterminated tails emit);
- `exec_inspect(id)` — `GET /exec/{id}/json` after EOF for the exit
  code the CLI reports as the `docker exec` status.

`Docker::try_exec_script` is the router. Served (code plus demuxed
streams, zero subprocesses) and Expired (step deadline hit: the CLI
watchdog's own 124 result — same message, same partial streams — with no
container kill: dropping the timed-out attempt closes the exec stream while
the container survives, exactly as on the CLI leg, where the watchdog's
parser hits the `--` separator and kills only the docker client) both
record `observe_api`; anything else returns `UseCli` and
the caller runs its historical CLI call unchanged, with the fallback
counter plus the fault at `warn`. The step deadline bounds the whole
attempt with no 5 s cap (payload takes the caller's deadline on both
transports); create/inspect sub-calls keep the capped API budget, and a
stalled create falls back to the CLI with its full deadline rather than
124ing the step. Under cancel the API attempt is abandoned and the CLI
fallback runs the same spawn-and-ladder-kill the CLI path always ran,
so cancellation keeps its historical shape by construction. Nothing on the
expiry path touches the daemon, so 124 returns on the deadline even against
a wedged daemon — no synchronous kill on the job thread.

Metrics semantics change with the engine on, deliberately: served nonzero
step exits and expiries record `observe_api` only, so the job summary's
`docker_failures`/`docker_timeouts` (per-host-invocation counts the CLI leg
bumps in `observe`) no longer move for migrated steps. Rationale: no host
`docker` invocation existed, so per-invocation counters must not move; the
step outcome lives in the step telemetry on both legs, and
`api_calls`/`api_fallbacks` carry the migration signal. Nothing in-repo
reads those summary fields back — they are log telemetry, not alert inputs.

Exec is the deliberate exception to the non-idempotent exclusion: a
fallback after the process started re-runs the step — only the rerun
reproduces the CLI leg's bytes. Safe cases (create refused, start never
connected) and rerun cases (ambiguous start, mid-stream fault, lost
exit code) share one contract — any API error falls back, every
fallback is telemetry-visible with its fault label — documented in the
module docs with narrowing to pre-start faults as a follow-up. The
deadline never falls back: expiry synthesizes, never retries.

TTY and detach semantics are preserved structurally: there is no TTY
or detach exec in the runner, the script-step shape carries no
`-t`/`-d`/`-i` by construction, and the engine document hardcodes
`Tty:false, Detach:false, AttachStdin:false`. Every other exec shape
(stdin forwards, adapter shells, host/maintenance calls) stays on the
CLI at its own untouched call site, as do test doubles (non-host
runners never route) and `VELNOR_DOCKER_ENGINE_API=0`.

Environment parity is structural, not asserted-after-the-fact:
`script_exec_env` replays the same three appends (base, step,
authoritative) onto a scratch builder and returns the recorded ordered
list, so daemon last-wins resolves identically without the daemon reading
an env file; the committed test reconstructs the CLI leg's effective env
(env files expanded in place, bare `-e` resolved) and pins exact
order equality including control-spoof drops, PATH override position,
authoritative re-assertion, and a multiline value the CLI can only
carry via the client process env.

One perf fix the large-output test forced: per-line front-draining in
the accumulator was quadratic (1 MB of short lines took 12 s);
single-pass split plus one drain took it to 0.07 s.

Out of this slice, deliberately: all other exec call sites
(`native_shell`, `container_docker` stdin, net/service/preflight
probes), narrowed pre-start-only fallback, connection reuse,
consecutive-failure short-circuit.

## Live findings (OrbStack Engine 29.4.0 / API 1.54)

Shell probes plus the committed `#[ignore]` bench (all probe objects
deleted, 0 containers remaining) fixed the truth table both legs
implement:

- API: create answers 201 plus `{"Id": ...}`; missing container is 404
  plus the `No such container` document; start answers `200 OK` with
  `Content-Type: application/vnd.docker.raw-stream` and NO length or
  chunked framing — close-delimited hijacked bytes; frames are stream
  id plus 3 zero bytes plus big-endian length (multi-line payloads in
  one frame observed); `Env` is last-wins (`A=1,A=2` reads `A=2`,
  proven); `WorkingDir` honored.
- Exit code: `Running:true, ExitCode:null` while running, set before
  the stream closes; the daemon normalizes to eight bits — `exit 300`
  reads 44 on BOTH transports, so the low-byte conversion matches the
  CLI's own process-exit truncation for every value.
- CLI: `docker exec` prints demuxed streams and exits with the step
  code; nothing about the CLI leg changed.

## Numbers

Subprocess count per run step (committed regression test
`script_exec_served_with_zero_subprocess_before_after_identity`):

- before (engine off): 1 `docker exec` subprocess per run step;
- after (engine on): 0 runner calls, byte-identical result.

Unlike slice 3's maintenance consumers, this is the per-job hot path:
a job with N run steps saves N subprocesses (plus N daemon-side env-file
reads) with no behavior change. The host-side env-file write+unlink per
step remains: the CLI args are built up front so the fallback vector is
ready and the secret audit still runs even when the API serves.

Latency, live trivial step (`echo out; echo err >&2; exit 3`), 10
iterations per leg, macOS arm64 via OrbStack socket (committed
`#[ignore]` bench `live_exec_latency_bench`, real client both legs):

- CLI p50 32.9ms / p95 36.1ms vs API p50 16.2ms / p95 17.8ms — ~2x.

The ~17 ms delta is one `docker` spawn; real steps are
daemon-work-dominated, so as with slice 3 the win is process count
(1→0 per step), not latency.
