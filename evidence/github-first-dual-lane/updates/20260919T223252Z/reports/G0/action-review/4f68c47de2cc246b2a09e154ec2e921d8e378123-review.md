## Blocking findings

### 1. Root manifest keys are not validated as runner strings

`validate_metadata_shape` obtains the root mapping and checks only known string
lookups (`crates/velnor-workflow/src/s2/scan/action.rs:399-418`). It never
validates every root key. The scanner therefore accepts non-string and empty
root keys even though the runner's root schema says `loose-key-type` is
`non-empty-string` (`actions-runner/src/Runner.Worker/action_yaml.json:2-14`),
and `ActionManifestManager` calls `actionPair.Key.AssertString(...)` for every
root entry (`ActionManifestManager.cs:90-97`).

Exact scratch fixture:

```yaml
1: unexpected-non-string-root-key
runs:
  using: composite
  steps:
    - shell: bash
      run: printf 'scanner-only\n'
```

`velnor-workflow --plain --dry-run --default-branch main` against
`/private/tmp/g3-action-fixtures-4f/root-nonstring` exited **0** and emitted a
`GitHub Action` unit with `velnor-workflow verify-action --path 'action.yml'`.
The empty-key variant at
`/private/tmp/g3-action-fixtures-4f/root-empty/action.yml` also exited **0**.
The exact `verify-action --path action.yml` command exited **0** for both.

This is malformed runner metadata hidden by scan. The candidate's own typed
runner parser also accepts the numeric key because the unknown key is ignored,
so this is not repaired downstream by the current Velnor contract.

Required fix: make the shared manifest parser/validator validate every mapping
key at the root as a non-empty string, while retaining the runner's loose
unknown-value behavior. Add numeric-key and empty-key negative fixtures.

### 2. Pinned external references admit unsafe source paths

`is_full_sha_action_reference` checks only the first two slash components and a
40-hex revision (`action.rs:688-704`). It accepts arbitrary later components,
including `..` and empty segments. The scanner consequently accepts:

```yaml
runs:
  using: composite
  steps:
    - uses: foo/bar/../../evil@0123456789abcdef0123456789abcdef01234567
```

and:

```yaml
runs:
  using: composite
  steps:
    - uses: foo/bar//evil@0123456789abcdef0123456789abcdef01234567
```

Both exact fixtures under
`/private/tmp/g3-action-fixtures-4f/{uses-traversal,uses-empty-segment}`
exited **0** in the scanner and emitted a GitHub Action unit. Exact
`verify-action --path action.yml` also exited **0**. No action script was
executed.

The exact Velnor runner comparator, built from the same detached source in
`/private/tmp/g3-action-comparator-4f`, rejected the same metadata during
`composite_action_invocations`:

- `foo/bar/../../evil@<sha>` → `unsupported repository action path '../../evil'`
- `foo/bar//evil@<sha>` → `unsupported repository action path '/evil'`

The rejection is implemented by the runtime's `action_dir` guard
(`crates/velnor-runner/src/action.rs:1339-1351`), after
`parse_repository_uses` accepts owner/repository plus an optional source path
(`action.rs:1221-1245`). A scanner-generated unit can therefore pass metadata
verification and later fail when the actual typed action planner expands the
same action. This is a real hidden runtime error, not an unsupported-runtime
skip.

The earlier minimum owner/repository hole is closed: the focused negative test
for `foo@<sha>` fails scan, and the pinned `octo/example@<sha>` consumer
fixture expands successfully. The remaining path grammar must be shared with
the runtime parser and must reject absolute, traversal, and empty path
segments. Add both negative forms and one valid owner/repository/path positive
fixture.

## Plugin boundary

The pinned runner schema explicitly contains `plugin-runs` with a non-empty
`plugin` field (`action_yaml.json:89-101`), and `ActionManifestManager` returns
`PluginActionExecutionData` when `plugin` is present without `using`
(`ActionManifestManager.cs:510-515`). The candidate's `ActionRuns` requires
`using`, so the valid fixture:

```yaml
runs:
  plugin: Example.Plugin
```

exited **1** with `parse GitHub Action metadata ... missing field: using`; it
did not emit a GitHub Action unit. This is fail-closed and must not be counted
as runner-equivalence proof. It is nevertheless not an explicit
`plugin unsupported` diagnostic/capability result. Either implement the
plugin contract or classify it explicitly as unsupported before generation;
retain a negative fixture proving no green unit is produced.
