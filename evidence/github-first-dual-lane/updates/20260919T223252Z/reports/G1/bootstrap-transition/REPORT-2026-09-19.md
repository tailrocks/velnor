## Why the candidate cannot bootstrap policy

The base-owned policy workflow at main `b5a4b4af` obtains and runs the
published validator `0dc79895ff1c5e88be7c3822c437e1c5b5282e12` before the
candidate path. Its generated entrypoint has the base `rev` in
`.github/workflows/ci-policy.yml` lines 59–72 and invokes the base process in
the final policy step (lines 167–180).

The source contract confirms the trust boundary:

- `policy::evaluate` calls `pin_rules` and then `semantic_rules`.
- `regenerate_and_compare` may use a manifest-bound candidate only in
  `render_with_candidate` (candidate renderer); it does not substitute the
  candidate into `semantic_rules`.
- The old validator's `is_github_owned_label` accepts `ubuntu-*`, `macos-*`,
  and `windows-*`, but not `xcode-27`; `classify_static_label` then reports a
  foreign runner when no provider selector matches.

Thus a PR artifact can prove a generator render in flight, not change the
trusted policy semantics. Using candidate bytes as the semantic validator,
using `--pin-build` in generated `pull_request_target`, bypassing Policy, or
using an unreviewed source checkout would break the stated trust contract.

## Two-phase option assessment

### Source-only policy admission, then pin adoption

The semantically correct staged shape is:

1. A reviewed source commit adds exact `xcode-27` admission and tests while
   leaving generated runner bytes unchanged.
2. Merge it with its hosted PR checks; run the mainline runtime publisher;
   verify the immutable product's closure, revision, all three asset digests,
   attestations, and manifest.
3. A separate reviewed pin-adoption commit updates generated pins to that
   published product; rerun clean and shallow checks.
4. Rebase PR957 on that pin. Its renderer then changes the generated Apple
   jobs and the product matrix to `xcode-27`; the already published validator
   can semantically admit that label. Publish/adopt the resulting generator
   product through another normal mainline epoch before declaring main green.

This is the only valid shape using the present candidate/base trust model. It
still necessarily executes the existing publisher's `macos-15` build during
step 2, because source-only policy support does not alter the generated
publisher matrix and the publisher cannot omit that required asset.

### Strict latest-version interpretation

If the user requirement means **no `macos-15` job may execute**, the option is
not executable with the current source and product contract. There is no safe
way to publish the policy-only product without either:

1. running the protected three-platform publisher as currently generated,
   including `macos-15`; or
2. changing the product contract to a separately typed, protected validator
   product/publisher with a complete attested platform scope, then reviewing,
   generating, publishing, and installing that new path before use.

The open PR959 (`381e0253d8e63a0ab4108177e1e23508d10989aa`) moves the renderer
to `macos-26`, but it is not a bootstrap bypass: its PR checks are green while
the base pin remains old, and merging generator output before a published
matching pin would leave the mainline generated-tree invariant stale. It also
does not satisfy the exact `xcode-27` requirement.

Official GitHub documentation currently lists `macos-15`, `macos-26`, and
`xcode-27` (public preview) as distinct arm64 labels; this does not make the
old label acceptable to the user's exact latest-label policy:
<https://docs.github.com/en/actions/reference/runners/github-hosted-runners>.
