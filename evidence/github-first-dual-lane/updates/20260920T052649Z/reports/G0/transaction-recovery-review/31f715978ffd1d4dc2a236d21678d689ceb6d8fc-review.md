## Residual boundaries / follow-up findings

### F1 — in-flight same-type swaps are not covered or atomically refused

The hostile fixture replaces the output with a symlink **before** recovery and
proves that the outside file is untouched (`src/s2/mod.rs:22189-22249`). It
does not swap a regular file after the final identity capture. The recovery
mutations still have a check/use window: `remove_transaction_output_at` captures
then calls `unlinkat` (`9099-9109`), and restore captures again then calls
`renameat` (`9172-9182`). A concurrent same-type replacement in either window
could remove/replace the pathname without being refused. No race injector or
concurrent hostile writer was run. Treat hostile symlink refusal as proven, not
general race immunity.

### F2 — descriptor anchoring is not the whole transaction path

`TransactionJournal::record` still captures the output with path-based
`capture_file_preimage` and writes progress through path-based `rename`
(`6734-6749`, `6940-6961`). Journal creation also uses path-based creation and
rename (`7169-7297`), and rollback still uses path-based capture/remove/rename
(`8723-8788`). Those paths perform identity checks, but they are not the
descriptor-rooted recovery path and have no deterministic hostile ancestor
swap fixture. A stronger local-adversary claim needs either the same anchor
boundary throughout or an explicit cooperative-writer scope.

### F3 — lock descriptor and recovery anchor are independently opened

Recovery acquires a lock on one `root` pathname (`7771-7778`; lock open at
`9598-9618`) and then separately opens the output-root descriptor by pathname
(`7035-7060`). If a privileged local writer renames/replaces the target root
between those opens, the lock and recovery anchors can refer to different
directories. This was not exercised. The existing tests establish ordinary
same-root serialization, not pathname replacement of the root itself.

### F4 — no process-crash or power-loss evidence

The six fixtures model interrupted writes and injected post-capture failures;
none kills the producer between journal/output boundaries, reopens after a
real process crash, or exercises storage power-loss ordering. The source
comment explicitly narrows `sync_all` to normal recovery ordering and says
tests do not attest crash-recovery semantics (`7147-7151`). Keep this as an
explicit non-claim; do not promote the test names “durable transaction” into a
power-loss guarantee.
