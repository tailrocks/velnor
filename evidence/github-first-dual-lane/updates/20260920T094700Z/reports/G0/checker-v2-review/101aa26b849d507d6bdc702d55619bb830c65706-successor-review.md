## Required follow-up

### F1 — Real Homebrew raw body is relabeled with `filter=all` (high)

The immutable corpus manifest records the Homebrew check-runs request as
`.../check-runs?per_page=100&filter=latest&page=1` with `total_count: 6`
(`crates/velnor-tools/src/testdata/g0/real-api-fixture-corpus-20260920-080318/fixture.json`).
The new actual-body positive attaches those same bytes to
`per_page=100&filter=all&page=1` (`evidence_check.rs:11620-11630`). The body is
real, but the request provenance is not: the test has synthesized a different
query to satisfy the hard-coded `filter=all` contract. This matters because
the checker claims query-to-response binding.

Either capture/use a body whose authenticated request really used `filter=all`,
or preserve the exact `filter=latest` request and encode an explicit
provider/coverage policy for it. Do not relabel the source request. Add a
fixture assertion tying the request metadata to the source manifest.

### F2 — Artifact rows are not bound to an `artifacts[]` member (high)

`check_g0_artifact_observations` validates the typed row's IDs, names, run
binding, URL, raw kind, raw digest, and exact list path
(`evidence_check.rs:3746-3836`), while the global stream check validates only
the page envelope/cardinality/IDs. It never parses the selected artifact row
and compares `artifact_id`, `name`, `expired`, run identity, or member digest
to an element of `artifacts[]`. A valid page can therefore be paired with a
caller-authored typed row naming a different member while retaining a valid
page digest and canonical archive URL. The complete fixture manufactures the
matching row/page ID and has no wrong-list-body negative.

Select the typed artifact from the exact `ArtifactsPage` response, then add
wrong-list-member/right-archive and rehashed-member negatives through the
inventory/public path. Keep the response-body digest distinct from the API
artifact archive digest: `crates/velnor-runner/src/protocol.rs:7285-7288`
uses `artifact.digest` to verify the downloaded archive, so comparing that
field to the raw list-page SHA conflates two different digests and is itself
not a valid member binding.

### F3 — Direct singular query parameters are still unconstrained (medium)

`g0_response_query_contract` returns `true` for every syntactically valid
query when the response schema is `Singular` (`evidence_check.rs:2518-2521`).
`g0_capture_raw_json` consequently accepts a direct check-run, suite, App, or
workflow-run request with arbitrary allowed `page`, `per_page`, `filter`, or
cursor parameters. If exact endpoint parameters are part of the contract,
singular routes must require the canonical empty query (or an explicit
allowlist), with a regression for `page=999`/filter injection.

### F4 — Unknown endpoint paths remain a generic-stream escape (scope note)

`g0_endpoint_is_paginated` recognizes a finite set of known list paths
(`evidence_check.rs:2480-2507`). An unknown `/repos/...` path is not marked
paginated; with an otherwise valid raw object,
`check_g0_paginated_response_streams` skips it and request provenance does not
emit `g0-response-schema`. Exact provider vectors still reject such a path,
so this is not a provider-relation bypass, but it is not a fail-closed
unknown-stream policy. Add a closed endpoint classifier for every retained
relevant stream or document that closure is provider-only.

### F5 — Actual supplement positive is helper-level, not full public inventory

`authenticated_supplement_binds_real_apps_and_suites` calls
`g0_check_raw_evidence_valid` directly with real body bytes. The public
serialized `check_paths` test uses the synthetic `complete_g0_fixture`; no
full `G0InventoryEvidence`/`check_paths` positive contains the approved
supplement. This is consistent with the explicitly unimplemented live
collector/all-32 authority, but must not be described as full live-entrypoint
coverage.
