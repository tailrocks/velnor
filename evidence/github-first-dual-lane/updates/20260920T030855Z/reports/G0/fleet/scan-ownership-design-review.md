# Scan ownership design constraints — pre-code review

Status: **design constraints only; no implementation approval**.

This review follows the exact rejection at `2c328e1d471546a2c9b4b1f7e790d1e3562c66d3`, recorded in `G1/scan-integrity/review2.md`. No source, generated workflow, host, or Docker changes were made.

## Architectural decision required

The `.github/ci/.github-actions-generator-state` sidecar cannot be an ownership authority. It is repository-writable. A digest, generated header, path allowlist, or sidecar schema can be useful cache/diagnostic data, but none can authorize scan invisibility, overwrite, or deletion by itself.

The rejected candidate proves the failure: `verified_recorded_output_paths` accepts current bytes when their digest equals the sidecar value (`crates/velnor-workflow/src/s2/mod.rs:6973-7003`), while `verify_generated_ownership` makes the same trust decision for writes (`:6790-6825`). A user can edit a current-renderer workflow and forge its deterministic FNV digest. The candidate also rejects sidecar entries absent from the current renderer (`:6984-6989`), which prevents legitimate stale-output removal before the later stale planner (`:6850-6883`).

## Feasible trust model

Ownership needs an immutable baseline supplied independently of the mutable worktree:

```text
TrustedOwnershipBaseline {
    baseline_commit: full immutable commit id,
    generator_revision: full pinned source/release revision,
    generator_closure: source-closure/release digest,
    render_schema: exact schema/revision,
    outputs: {
        typed repository-relative path -> immutable Git blob/content identity
    },
}
```

Acceptable baseline sources, in descending trust:

1. A protected base commit/object database read, with the base policy validator proving the pinned generator revision and source closure. The existing D19 path already describes this trust boundary: the base `policy` validator regenerates using the pinned generator and requires byte identity (`crates/velnor-workflow/README.md:10-25`, `crates/velnor-workflow/src/s2/mod.rs:5580-5591`).
2. A published, pinned generator release/source closure plus a caller-attested baseline revision. The public revision string alone is not trust; reachability and closure/byte identity must be checked by the trusted caller.
3. An explicit operator-supplied immutable baseline commit for local, non-policy generation. This is user authorization, not an unattended security claim; record that trust mode in diagnostics.

If no independent baseline is available, fail safe: do not hide `.github` inputs and do not delete stale outputs. Generate a plan requiring explicit reconciliation/adoption. Never silently promote the mutable worktree, config, sidecar, generated header, or current digest to “trusted.”

The current renderer and typed path registry remain useful, but only as a candidate path set. `current renderer owns path` is not proof that current bytes are generated. A current render may be used as an exact-byte comparison after the scan; it cannot authenticate the bytes that shaped the scan.

## Separate two decisions

### 1. Scan classification

Use a typed state per path:

```text
UserInput
GeneratedCurrentExact       // baseline/current renderer proves exact bytes
GeneratedStaleExact          // baseline proves old generated bytes
ModifiedGenerated            // typed path, bytes differ
ForeignOrUnknown             // no trusted baseline/path binding
```

Only `GeneratedCurrentExact` may be excluded from a subsequent scan pass. `ModifiedGenerated`, `ForeignOrUnknown`, and all unproven `.github` paths remain visible inputs and must cause an ownership conflict before any write. A sidecar entry may accelerate lookup but cannot create any of these states.

### 2. Mutation authorization

Classification never grants write/delete permission. The write plan must independently verify:

- canonical repository-relative typed path;
- no symlinked output root or managed ancestor;
- reviewed file identity and bytes immediately before replacement/deletion;
- exact trusted baseline preimage for stale deletion;
- no concurrent change after planning.

`--check` is read-only and fails on `ModifiedGenerated`, unknown ownership, stale metadata, or missing baseline. It must report config-input drift before trying an unrelated render of an invalid/obsolete declaration.

`--force` is explicit user authorization to replace a path the *current renderer* emits. It is not provenance, does not make sidecar text trusted, does not hide a modified path from scanning, and does not authorize deletion of an unproven stale path. A stale path may be deleted automatically only when it is present in the independent baseline and its current bytes exactly equal the baseline bytes. If those bytes differ, `--force` still refuses by default; a separately named, path-specific destructive removal mode would be required, with a displayed plan and preimage check.

## Required ordering

1. Load the independent baseline, or enter explicit no-baseline fail-closed mode.
2. Read config and compute config-input identity before renderer validation; this preserves the positive config-drift error even when a declaration is obsolete.
3. Scan with no sidecar-derived exclusions. Render the current typed surface from that scan.
4. Compare only baseline-bound/current-rendered paths and exact bytes. Classify each path; never use sidecar digest equality as proof.
5. If any `ModifiedGenerated`, `ForeignOrUnknown`, or baseline inconsistency exists, return a conflict/no-write result. Do not mutate the sidecar.
6. Build a mutation plan. Current exact paths may be refreshed; stale exact baseline paths may be removed; unknown/mismatched stale paths remain untouched.
7. Apply only after preimage revalidation. Write the new sidecar/cache last, and treat it as an advisory projection of the trusted result.

This ordering prevents both rejected classes: a forged current file cannot disappear from scan provenance, and a legitimate removed output can be deleted only from a trusted old baseline.

## Fixtures required before source approval

Use a valid currently supported declaration (`rust-crate-pipeline`, not the old `rust-crate` fixture that masked the candidate regression).

### Positive

1. **Config drift with unchanged outputs**
   - Generate from trusted baseline `B`.
   - Change one config policy field, e.g. `dco_required = false` to `true`, leaving generated bytes unchanged.
   - `--check` fails specifically with `config input changed`, before unrelated primitive/render errors; no files change.
   - Regeneration refreshes the trusted projection/sidecar and leaves output bytes exact; the following `--check` passes.

2. **Legitimate stale generated output**
   - Baseline `B` contains `old.yml` and its exact immutable bytes.
   - New trusted config/render omits `old.yml`.
   - Exact baseline bytes permit stale deletion and removal from the new projection.
   - Editing `old.yml` first makes both normal generation and `--force` refuse deletion; bytes remain unchanged.

### Negative

1. **Forged current content plus forged digest**
   - Edit a current-renderer workflow/action to add a user trigger, action, permission, or step.
   - Change sidecar digest to the exact digest of the edited bytes.
   - Scan must not exclude it; `--check` must fail; ordinary generation must preserve it and refuse overwrite. `--force` may replace it only under the explicitly documented current-path force policy, never because the sidecar matched.

2. **Forged untyped path**
   - Add a sidecar entry for an unmanaged workflow/composite action.
   - It remains visible, is never stale-deleted, and cannot be authorized by `--force` unless separately selected as a current typed output.

3. **Spoofed generated marker**
   - Add a user file beginning with the exact generated header but absent from the independent baseline/current renderer.
   - It remains user input and is never treated as owned.

4. **Traversal/symlink path**
   - Exercise `.//.github`, `./.github`, `..`, absolute paths, and source/output symlinks.
   - Reject before scan exclusion or mutation.

5. **Concurrent replacement**
   - Change bytes or file identity after plan capture.
   - The preimage check fails and preserves the replacement; no sidecar refresh occurs.

## Design approval gate

Reject any proposed design that:

- uses sidecar/header/hash/path naming as the sole ownership proof;
- hides modified bytes merely because the path is in the current renderer;
- deletes stale paths from sidecar claims without an independent old baseline;
- lets `--force` convert unknown ownership into trusted ownership;
- conflates scan exclusion with overwrite/deletion authorization;
- emits only an aggregate result without the path classification and preimage reason.

Approve design only after it names the independent baseline source, no-baseline behavior, `--force` semantics, and the five positive/negative fixture classes above. Then review one immutable source commit; do not review an implementation worktree while it is changing.
