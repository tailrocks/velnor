### 2. Scratch quota does not cover all storage surfaces

`candidate_transport_scratch_setup_script()` creates and mounts the ext4 image at `mod.rs:149-176`, and later shell steps export `RUNNER_TEMP` to that mount. That does not cover all paths:

- Producer `actions/checkout` downloads `candidate-control` and `candidate-source` before scratch setup (`ir.rs:3043-3060`); those workspaces are ordinary `$GITHUB_WORKSPACE` paths. Policy checkout also precedes scratch setup (`mod.rs:5529-5548`).
- `actions/download-artifact` and `actions/upload-artifact` are action processes. Their `path` points below `runner.temp`, but the generated action steps do not set `RUNNER_TEMP` to the mount. Only later shell steps export it (`mod.rs:5558-5567`, `5850-5857`). Action-internal staging/temp therefore remains unproven outside the ext4 quota.
- Docker image pulls/layer storage are daemon-managed outside the mounted path (`ir.rs:3096-3103`; `mod.rs:5664-5675`). Builder `/target` and sandbox `/tmp`/`/output` tmpfs limits are useful container limits, not host Docker-store quota.
- Scratch setup itself writes the image and marker files in the parent runner temp (`mod.rs:156-175`), and all initial checkout/source bytes remain outside the image.

This fails the requested “ALL downloads/extractions/source/output/temp” boundary unless the owner narrows that requirement and independently bounds these surfaces.

### 3. Stream/pre-allocation limits are incomplete

The artifact paths use `curl --max-filesize 268435456` and then `stat` for ZIP downloads (`mod.rs:5339-5347`, `5977-5985`, `6083-6090`, `6168-6175`). The action archive helper also uses `--max-filesize` but has no post-download size check (`mod.rs:5195-5201`, repeated at `5959-5965`). No curl version/unknown-length behavior is asserted and no bounded streaming wrapper writes to a temporary file before rename.

More directly, trusted source archives are written through shell redirection and only measured afterward:

- namespace scan writes complete base/head repositories with no size/member bound (`mod.rs:4713-4717`);
- acquire writes `handoff/source.tar`, then hashes/stats it (`mod.rs:5404-5412`);
- verifier writes `verifier-source.tar`, then stats it (`mod.rs:6266-6271`).

The namespace scan Python reader also has no total member/declared-byte limit (`mod.rs:4717-4800`). Thus a source tree or archive can consume the fixed filesystem before the later check. This is an outstanding B1 blocker, not closed by the post-write `stat` checks.

### 4. Mount/unmount failure atomicity is not proven

The setup script has `set -euo pipefail` but no `trap`; a failure after `mount` and before both marker files plus `$GITHUB_ENV` export leaves a live mount without a discoverable cleanup record (`mod.rs:154-176`). Cleanup requires both marker files and `findmnt` success before unmount (`mod.rs:184-193`), so it cannot recover that partial state. Producer cleanup is `if: always()` but has `working-directory: candidate-control` (`ir.rs:3190-3198`); a failed checkout can make that directory unavailable. A failed `sudo umount` intentionally stops before removing the image, but there is no bounded recovery/rollback proof. No Linux mount-failure fixture was run on this Darwin host.

The `df` check also compares filesystem total capacity (`df ...` column 2) with the exact image byte count (`mod.rs:171-173`). Ext4 metadata/reserved-space behavior was not exercised on Linux here, so the setup's usable-capacity assertion remains unverified rather than accepted.
