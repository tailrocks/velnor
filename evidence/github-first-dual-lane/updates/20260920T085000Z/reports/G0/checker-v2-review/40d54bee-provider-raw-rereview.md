## Blocking findings

### F1 — Missing envelope is accepted as a valid paginated response (high)

`g0_select_raw_member` only enters strict envelope validation when the expected
key is present. Otherwise it falls back to `value.id` (`evidence_check.rs:3912-3942`).
It does not classify the request endpoint, require `items_returned == 1`, or
reject a singular body on a list endpoint.

The regression fixture demonstrates the hole: `push_provider_raw_fixture`
emits a bare `{id,...}` job body while recording the documented attempt-list
endpoint `/actions/runs/{run}/attempts/{attempt}/jobs`
(`evidence_check.rs:8280-8302`). The positive
`captured_app_and_actions_objects_bind_raw_provider_fields` test then accepts
that malformed page (`:10937-10949`). A response from the attempt-list or
commit check-runs route must contain its documented envelope and matching
cardinality. Only an explicitly allowlisted official singular endpoint may
return one object. If singular job support is desired, use
`/repos/{owner}/{repo}/actions/jobs/{job_id}`; never restore the old
`/actions/runs/{run}/jobs/{job}` path.

### F2 — Positive App/suite/provider proof still synthesizes the critical bodies (high)

The archive contains real run, attempt, jobs, artifacts, check-runs, and
separate Sonar bodies, but no independently captured `/apps/{slug}` or
`/check-suites/{id}` bodies. The real-corpus test therefore checks App/suite
fields nested inside a check-run, but never runs the complete
`g0_check_raw_evidence_valid` chain over actual App/suite/run/job raw objects.

The only complete positive chain is still generated by
`push_provider_raw_fixture` (`evidence_check.rs:8200-8305`), which constructs
canonical JSON from the typed IDs. Its two raw mutations prove the generated
fixture rejects those mutations, not that the producer captured the provider
objects. Add actual immutable App, suite, workflow-run, and attempt-jobs
bodies (or explicitly keep the chain unavailable) and mutate those actual
bytes for wrong-App, wrong-suite, not-in-jobs, and backlink negatives.

### F3 — Advertised paginated check-suite route has no envelope selector (medium)

`g0_check_raw_evidence_valid` permits
`/repos/{repository}/commits/{sha}/check-suites`
(`evidence_check.rs:3964-3969`), but `g0_select_raw_member` only recognizes
`check_runs` and `jobs` envelopes (`:3918-3920`). A valid GitHub
`{total_count,check_suites:[...]}` response is treated as a singular object
and rejected. Either add exact `check_suites[]` pagination selection and
completeness checks, or remove that list route from the accepted endpoint set;
do not leave a valid route half-supported.

### F4 — Pagination completeness is page-local, not stream-complete (medium)

`g0_capture_raw_json` requires exactly one raw candidate per object kind
(`evidence_check.rs:3878-3888`), and `g0_select_raw_member` compares a final
page's `total_count` only with that page's member count
(`:3926-3939`). It does not aggregate all captured pages, reject duplicate
non-target IDs, or prove that the sum of page cardinalities equals the API
`total_count`. The frozen corpus happens to be one page (68 jobs and 70
check-runs), so its positive test cannot establish multi-page completeness.
Either constrain and document the producer to complete single-page captures,
or bind all pages in the stream and validate contiguous links, total count,
unique IDs, and target membership over the complete set.
