# A1: Runtime-products publish 403 — run 35157890866 (f16cc51a)

## TL;DR
`gh release create $TAG --target f16cc51a` 403'd **not** for lack of `contents:write`
(it had it) but by GitHub's Nov-2023 **workflow-scope enforcement on release
creation** (cli/cli#9514): with an explicit `--target`, the API diffs
`target..HEAD`; that range contained workflow files (commit 386ccc16 touched
12× `.github/workflows/*.yml`), so the call additionally required
`workflows:write` — a scope **GITHUB_TOKEN can never hold** → `HTTP 403:
Resource not accessible by integration`. Systematic-under-overlap, not flaky.

## Why each suspect is ruled in/out
- **Perms/token**: OUT. Publish banner: `Contents: write`; `GH_TOKEN:
  github.token` (own job token, `publish.permissions.contents: write`).
  403 message is GitHub's generic surrogate, not a real scope deficit.
- **Concurrent-publish race (two POSTs, one tag)**: PARTIAL. No two POSTs
  raced (run 2's POST came 100s later and succeeded). The race is
  **stale-target vs fresh-HEAD**, plus a pre-existing tag (second,
  corroborating 403 trigger per chipsenkbeil/distant#284).
- **Tag-exists path**: behaved correctly (miss→create; later hit→skip).
  It is blind to this conflict class (dirty-range/tag-mismatch → 403,
  not 422/"already exists").
- **Branch/ref of dispatch**: OUT (both `push` to `main`). NOTE: branch
  dispatches *do* share closure tags with main (release ff27… targets
  dispatch-branch commit 294cea83) — a live cross-ref collision surface
  the same-ref concurrency group does not cover.
- **Neighbors 35158058879/35159518917**: succeed by construction
  (fresh-target-201 / published-row-skip), confirming the trigger is
  staleness + workflow-delta, not environment.

## §4 The created_at side-finding (all 14 recent runtime releases)
Every runtime release shows `created_at` ≈ run-created − ~10s and
`published_at` ≈ publish-step time (~2.5min gap = resolve+build).
Verified 4/4: `created_at` == **tag-creation time** (runtime tags are
created same-second-as-commit by routine external pre-tagging; v0.1.274:
created 21:49:57 = tag-push, 44s after its commit 21:49:13).
So an external actor (bastion operator/watcher) tags every push's closure
*before* workflow runs exist; the workflow is not the sole tag-writer
(split-brain ownership, second 403 trigger, must be resolved — see F6).

## Why the architecture allowed it
1. Same-ref concurrency serializes run *start*, not publish *freshness*:
   run 1 may publish after run 2's push (serialized-yet-stale).
2. No mutex on the true shared resource — the **closure tag**: stable
   closure across back-to-back pushes (pin-bumps, docs) = same tag from
   two commits = race by construction. Cross-ref (dispatch vs push)
   shares tags with zero serialization.
3. `--target $HEAD_SHA` (build-time SHA, stale-by-design under 1+2)
   walks straight into the workflow-scope trap whenever the range
   carries workflow files.
4. `gh release view` pre-guard + gh's published-only pre-check cannot see
   this conflict (dirty range / tag-mismatch surface only as POST 403).
5. External routine tag pre-creation doubles the race surface.

## Transient or systematic?
**Systematic-under-overlap**: deterministic given (a) back-to-back main
pushes with unchanged closure, (b) workflow files in stale-target..HEAD,
(c) older publish landing after newer push. Not flaky, not every-run.
Recurrence scales with main-push velocity × workflow-file churn —
bastion-campaign conditions. First observed 403 of this kind (18:xx
failures were smoke-test and exit-126 — different causes).

## Cascade claim ("Planning-race failures #5 on next main")
**Contradicted as a cascade of the 403**: CI/Main + Preview failed
*before* it on both commits (f16cc51a: 22:29:16/31 < 22:31:29;
386ccc16: 22:31:15/35). The release exists since 22:33:12, so 33688938
consumers resolve/download fine. Treat Preview/Planning failures as a
separate incident, not downstream of this 403.

## Proposed source fix (no edits made)
- **F1 (preferred): stop targeting stale SHAs with GITHUB_TOKEN.**
  `--target main` resolved fresh in publish, or drop `--target` (API
  defaults to default-branch HEAD; cf. distant#284), or push the tag
  explicitly first then `create --verify-tag` without `--target`
  (cf. tommy-xr/functor#398). Closure tag still names the product;
  build provenance (attestations) still pins the build commit.
- **F2 (required regardless): conflict → converge, not fail.**
  On create failure, re-view with wait/retry; if a published release
  appears, skip-as-success (attest/smoke winner or `skipped=true`).
  Fail only if nothing materializes. Same for gh's "already exists".
- **F3: serialize on the tag, cross-ref.**
  `concurrency.group: runtime-products-${{ needs.closure.outputs.tag }}`
  so same-closure main-push and branch-dispatch runs never publish
  concurrently.
- **F4: freshness re-check in publish (pre-create).** If `origin/main`
  moved past `$HEAD_SHA` with unchanged closure (recompute at tip —
  cheap, no build), skip: the fresher run owns the tag. (Resolve-time
  check is insufficient — staleness arose mid-build here.)
- **F5 (reject): App-token/PAT with `workflows:write`.** Converts the
  403 into a stale-target 201 — masks the race, invites dual-write.
- **F6: single tag-writer.** Either the workflow or the external
  pre-tagger owns tag creation — delete the other path (no shims).
