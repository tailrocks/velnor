# Trust scope

Trust scope is the operator-selected ceiling that bounds what a job on this
node may reach and which persistent stores it shares. It is set once, by the
operator, for the whole pool. Each job's scope in effect — its admitted scope —
is that ceiling narrowed by the job's own trust class, which Velnor derives
from the job's event: a same-repo job is trusted, a fork pull-request job or a
job whose trust signals are missing is untrusted. A fork pull request cannot
widen the ceiling, and on a trusted pool it still executes on the untrusted
path: no host Docker socket, no user secrets, untrusted store namespace.

## The default is `untrusted`, and it fails closed

`VELNOR_TRUST_SCOPE` (or `--trust-scope`) defaults to `untrusted`. Absent,
empty, or unrecognized values all resolve to `untrusted`. Only the exact value
`trusted` grants capability; `release` selects the `release` store namespace
with the same capability as `untrusted`.

### Breaking change for existing deployments

The default used to be
`trusted`, and the two binaries disagreed about which value was in force. A
node upgraded without changing its configuration loses the host Docker socket,
privileged container options, privileged service containers, host port
publishing, and the right to run a job carrying user secrets. Its persistent
stores also move into the `untrusted` namespace, so the first job after the
upgrade rebuilds its caches once.

**What an operator must do:** if the pool is meant to run trusted work, set
`VELNOR_TRUST_SCOPE=trusted` in `/etc/velnor/velnor.env` explicitly and restart
the daemon. If it is meant to run fork or public work, change nothing — the new
default is the correct one.

## What `trusted` unlocks

The table below is what a trusted pool grants a trusted job. Either side can
refuse: a trusted job on a pool below `trusted` gets the untrusted column,
and a fork or unknown job gets the untrusted column on every pool.

| Capability | untrusted path | trusted pool + trusted job |
| --- | --- | --- |
| Host Docker socket mounted into the job | refused | allowed |
| Privileged job-container options | refused | allowed |
| Privileged service containers | refused | allowed |
| Host port publishing | refused | allowed |
| A job carrying GitHub user secrets | job refused before execution | allowed |
| BuildKit secrets for `docker/build-push-action` | refused | allowed |

A job that arrives with user secrets on the untrusted path is refused by
name before any side effect, not silently stripped.

## Store partitioning

Every executable or build store Velnor persists across jobs is partitioned
first by trust class and then, where a repository identity applies, by numeric
GitHub repository ID:

```text
<storage root>/cache/velnor/v1/<untrusted|trusted|release>/<class>[/<repository id>]
```

With the packaged storage root that is `/var/cache/velnor/v1/...`. The
partitioned classes are the Mr Boxington store (`compiler/mbx`), the sccache
store (`compiler/sccache`), `$CARGO_HOME/bin`, the mise install and binary
stores, the Cargo target generation store, and the Playwright browser store.

Partitioning exists so compiled state, installed toolchains, and anything else
on a later job's `PATH` cannot cross a trust boundary. It is a cache-reuse
boundary. It is not encryption, and it is not protection from a compromised
host.

Daemon-shared stores that hold no executable content — the Cargo registry
cache, registry index, and Git database — stay warm across scopes in the
legacy layout, where trust is namespaced below the shared root. In the
canonical layout the root itself is namespaced by the job's admitted scope,
so a fork job's download caches are cold there too: isolation first, warmth
second.

A missing or invalid repository identity fails closed to a job-ephemeral store
rather than sharing one.
