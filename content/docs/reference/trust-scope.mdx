# Trust scope

Trust scope is the operator-selected ceiling that bounds what a job on this
node may reach and which persistent stores it shares. It is set once, by the
operator, for the whole pool. Each job's scope in effect — its admitted scope —
is that ceiling narrowed by the job's own trust class, which Velnor derives
from the job's event: a same-repo job is trusted, a fork pull-request job or a
job whose trust signals are missing is untrusted. A fork pull request cannot
widen the ceiling, and on a trusted pool it still executes on the untrusted
path: no host Docker socket, no user secrets, untrusted store namespace.

## The default is `untrusted`, and it fails closed

`VELNOR_TRUST_SCOPE` (or `--trust-scope`) defaults to `untrusted`. Absent or
whitespace-only values resolve to `untrusted`. Capability checks trim the
value and match `trusted` case-insensitively. Store keys preserve each
non-empty trimmed value: `release` and other custom labels keep distinct
namespaces but do not grant trusted capabilities. The namespace key is based
on the trimmed spelling, so case variants can use separate namespaces even
when the capability check treats them alike.

### Breaking change for existing deployments

The default used to be
`trusted`, and the two binaries disagreed about which value was in force. A
node upgraded without changing its configuration loses the host Docker socket
mount on supported Linux Docker hosts,
privileged container options, privileged service containers, host port
publishing, and the right to run a job carrying user secrets. Its persistent
stores now resolve in the `untrusted` keyed namespace, so the first job may
start cold because old raw-scope paths are not reused by the keyed layout.

**What an operator must do:** if the pool is meant to run trusted work, set
`VELNOR_TRUST_SCOPE=trusted` in `/etc/velnor/velnor.env` explicitly and restart
the daemon. If it is meant to run fork or public work, change nothing — the new
default is the correct one.

## What `trusted` unlocks

The table below is what a trusted pool grants a trusted job. Either side can
refuse: a trusted job on a pool below `trusted` gets the untrusted column,
and a fork or unknown job gets the untrusted column on every pool.

| Capability | untrusted path | trusted pool + trusted job |
| --- | --- | --- |
| Host Docker socket mounted into a Docker-backend job | refused | allowed on supported Linux hosts; suppressed on macOS until a VM-reachable per-job lease proxy exists |
| Privileged job-container options | refused | allowed subject to the option filter below |
| Privileged service-container options | refused | allowed subject to the option filter below |
| Host port publishing | refused | allowed |
| A job carrying GitHub user secrets | job refused before execution | allowed |
| BuildKit secrets for `docker/build-push-action` | refused | allowed |

A job that arrives with user secrets on the untrusted path is refused by
name before any side effect, not silently stripped.

For Native jobs, trusted scope does not allow a workflow to add volume-backed
or host-path mounts, or Docker API socket access, through outer job or service
container options. Velnor strips user-supplied `-v`/`--volume`, `--mount`,
`--volumes-from`, `--volume-driver`, `--volume-opt`, and `--use-api-socket`
options before launch, regardless of trust scope. Runner-owned
workspace, cache, tool, and eligible Linux host-socket mounts are constructed
separately; the socket mount remains limited to trusted jobs on supported Linux
hosts.

## Store partitioning

Canonical trust-scoped cache stores are partitioned by the job's admitted
scope — the pool ceiling narrowed by the job's trust class — and use a keyed
sibling root. The repository key is class-specific:

```text
<cache root>__trust_scope_v1/trust-scope-v1-<digest>/<class>/...
```

For example, the packaged cache root is `/var/cache/velnor/v1`, and its keyed
namespace is `/var/cache/velnor/v1__trust_scope_v1`. The filesystem component
is `trust-scope-v1-<digest>`, derived from the normalized scope; it is not the
raw scope label. The layout does not migrate, reuse, or read prior raw-scope
directories under `v1`. The Debian package's guarded `storage purge-legacy`
step removes supported old roots only for packaged instances still present in
configuration. Undiscoverable custom roots, roots for deconfigured instances,
and unsupported old layouts may remain outside the keyed catalog, absent from
current cache reports and GC while still consuming disk.

On a `trusted` pool, trusted jobs normally use `trusted` and fork or unknown
jobs use `untrusted`. Same-repository pull-request events on exactly the
`trusted` pool use the `pr` store scope; their Cargo download store is seeded
from `trusted` before the container starts. This changes store scope, not the
job's trust class. On a `release` pool, trusted jobs use `release`; on a custom
pool they keep that pool's scope. Fork and unknown jobs still use `untrusted`.
The effective scope determines store paths and mounts. Classes with active
writers publish matching `ScopeLease`s; the GHA cache service instead uses
token-bound job identity sessions, and retired `targets` has no active writer.

Among cataloged cache stores, the key types are:

- Cargo registry/Git downloads and mise download cache use trust scope only.
- `$CARGO_HOME/bin`, mise installs and binaries, and the shared `caches` root
  (local `actions/cache`, Playwright, Bun, npm, and Terraform plugin caches)
  use trust scope plus sanitized `github.repository`. `actions/cache` adds its
  compatibility version and cache key below that repository path.
- Mr Boxington (`compiler/mbx`) and explicit sccache (`compiler/sccache`) use
  trust scope plus numeric `github.repository_id`; MBX keeps cache and managed
  targets in per-slot subtrees.

Active non-MBX Cargo targets live in per-slot `stable-workspaces`, outside the
store catalog, keyed by admitted scope and numeric repository ID. The
cataloged `targets` class is retired and has no active writer; it remains for
cleanup of residual persistent target generations.

Partitioning exists so compiled state, installed toolchains, and anything else
on a later job's `PATH` cannot cross a trust boundary. It is a cache-reuse
boundary. It is not encryption, and it is not protection from a compromised
host.

The Cargo registry cache, registry index, Git database, and mise download
cache are trust-scoped and shared across slots, but not across trust scopes in
the canonical layout. Repository identity does not further partition these
download stores. A fork or unknown job therefore uses a separate download
store from trusted work.

For a store that needs repository identity, a missing or invalid value fails
closed to job-ephemeral storage rather than sharing one.

## Admission record

Trust derives before the admission row persists, so every admitted job is
auditable: the row carries the job's trust class (`trusted`, `fork-pr`,
`unknown`) and the effective admitted scope it runs with, and the job's
telemetry observations carry the same two values as `trust_class` and
`trust_domain`. Rows admitted before this record existed keep a null class,
and only rows admitted after it are guaranteed to carry the effective scope
rather than the pool ceiling.
