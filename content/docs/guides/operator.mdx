# Operator guide

This guide covers Debian installation, service operation, release changes, and
the command surfaces currently available. Velnor is research software; use a
dedicated host and test repository.

> Navigation: [← Documentation index](/) · [Observability →](/operations/observability)

## Install a release on Debian

Velnor currently publishes `.deb` files and matching checksum assets as GitHub
Release assets. This repository does not provide an APT signing-key bootstrap
URL or an APT repository setup procedure. Download the exact approved release
asset and verify its checksum before installation.

```sh
sha256sum --check velnor-runner-VERSION-ARCH.deb.sha256
sudo install -d -m 0750 /run/velnor
sudo /usr/bin/flock --exclusive --nonblock --no-fork \
  /run/velnor/package-transaction.lock \
  apt-get install ./velnor-runner-VERSION-ARCH.deb
```

Replace `VERSION` and `ARCH` with the downloaded asset names. Direct `dpkg -i`
and unlocked package transactions are rejected. Installation verifies package
identity, creates required paths, reloads systemd, enables the weekly
`velnor-cache-gc.timer`, and does not activate a release or restart the fleet.
Fresh installs leave fleet services disabled and stopped; upgrades preserve
their existing enablement state.

Install host prerequisites before the package and backend prerequisites before
starting the daemon:

- systemd, outbound HTTPS, Git, curl, CA certificates, util-linux, and enough
  CPU, memory, and disk for the selected jobs;
- Native Docker backend: a running Docker daemon and the required host Docker
  socket;
- Native microVM backend: `/dev/kvm`, packaged verified Firecracker artifacts,
  and a working jailer. MicroVM never falls back to Docker;
- Optional Scale Set lane: a running host Docker daemon to manage the official
  runner and its private DinD containers; its per-worker daemon does not use the
  host Docker socket. Velnor creates each DinD container with
  `docker create --privileged`, so the host must permit privileged container
  creation. Use this lane only where the host's trust boundary allows it.

## Configure and start

Edit the default-scope files:

```sh
sudoedit /etc/velnor/velnor.env
sudoedit /etc/velnor/execution.toml
if sudo test ! -e /etc/velnor/secrets.env; then
  sudo install -m 0600 /dev/null /etc/velnor/secrets.env
else
  sudo chmod 0600 /etc/velnor/secrets.env
fi
sudoedit /etc/velnor/secrets.env
```

Set the native lane's backend, with no fallback:

```toml
[execution]
backend = "docker" # or "microvm"
```

Keep the operator GitHub token in `/etc/velnor/secrets.env`:

```text
GITHUB_TOKEN=...
```

Keep it out of command arguments, shell history, and workflow files. The token
must authorize runner registration for the configured repository, organization,
or enterprise and any selected runner group.

The main environment file defines the GitHub scope, runner name and labels,
slot count, trust scope, capability validation, and work directory. Capability
validation must be `strict`. Organization and enterprise scopes require an
explicit runner group and a matching desired routing policy.

The daemon runs native slots only by default. To configure the official Scale
Set lane, set `VELNOR_SCALE_SET_CONFIG` in
`/etc/velnor/velnor.env` to its TOML configuration; for a named
`velnor-daemon@NAME.service`, set it in `/etc/velnor/NAME.env`. Its App key or
PAT must be referenced from the service's mode-`0600` secrets file or a private
credential file. The Scale Set adapter shares the host-wide permit ledger with
native slots. See the
[Scale Set configuration reference](/reference/configuration#optional-scale-set-lane).

Before enabling any daemon, create the host demand-source roster. Each daemon
reads this root-owned file and fails closed unless its own state database,
configured Scale Set database, and native slot marker roots appear in it. The
roster is host-wide, so list every daemon's paths, not only the first daemon's.
Include the shared permit ledger, every daemon state database, each Scale Set
database, and every native slot marker root. List each Scale Set database
under both `state-db` and `demand-db`; if it shares a daemon state database,
list that path once under `state-db` and once under `demand-db`. Set
`VELNOR_PERMIT_LEDGER` identically for every daemon unit so each resolves the
single ledger path in this roster:

```sh
# New-host bootstrap only, before starting any daemon:
sudo install -o root -g root -m 0644 /dev/null /etc/velnor/permit-ledger.sources
sudo install -o root -g root -m 0644 /dev/null /etc/velnor/permit-ledger.sources.lock

# Every roster edit, including the initial population, holds this lock:
sudo /usr/bin/flock --exclusive --wait 30 \
  /etc/velnor/permit-ledger.sources.lock \
  /usr/bin/sudoedit /etc/velnor/permit-ledger.sources
```

Use the actual absolute paths resolved by the configured units:

```text
permit-ledger /absolute/path/to/shared/permit-ledger.db
state-db /absolute/path/to/daemon/state.db
demand-db /absolute/path/to/scale-set/demand.db
native-slot /absolute/path/to/native/slot/marker-root
```

Add one entry for each distinct path within each kind; a Scale Set database
appears once under both `state-db` and `demand-db`. The roster must remain
root-owned, readable, and not group/world-writable. Keep its sibling lock file
root-owned with mode `0644`; the daemon opens it read-only. Create the lock once
before the first daemon starts, keep its inode stable, and never replace or
remove it while any daemon is active. Before enabling any daemon, create every
database file and native marker directory named in the roster, with access for
the configured daemon account. Hold an exclusive `flock` on the sibling lock
for the full duration of every roster edit; daemons use a shared lock while
reading it.
Update the roster before starting any added or changed daemon, database, or
native slot root; restart all daemons after changing the roster.

`VELNOR_TRUST_SCOPE` applies to native slots only. It defaults to `untrusted`
and fails closed: an untrusted native job loses the host Docker socket,
privileged container and service options, host port publishing, and permission
to run with user secrets; its persistent stores move to the `untrusted`
namespace so the first job rebuilds its caches once. Set
`VELNOR_TRUST_SCOPE=trusted` explicitly if that is what the native pool is
for. Scale Set config has no `trust_scope` field, and its private DinD is
created with `docker create --privileged`; allow it only on a host whose trust
boundary permits privileged containers. See [Trust scope](/reference/trust-scope).

Start the services explicitly:

```sh
sudo systemctl enable --now velnor-guardian.service
sudo systemctl enable --now velnor-daemon.service
sudo systemctl enable --now velnor-doctor.timer
```

The guardian provides local supervision only. The daemon opens durable state,
selects storage, preflights the backend, admits capacity, and supervises slots.
Each slot performs its own JIT registration before polling GitHub. Registration
and network failures retry in-process with backoff; a retrying daemon is not a
healthy or schedulable fleet.

For another scope, create matching files and use the template units:

```sh
sudoedit /etc/velnor/NAME.env
sudoedit /etc/velnor/NAME.secrets.env
sudo chmod 0600 /etc/velnor/NAME.secrets.env
sudo systemctl enable --now velnor-daemon@NAME.service
sudo systemctl enable --now velnor-doctor@NAME.timer
```

State for a named instance is kept below `/var/lib/velnor-NAME`.

## Verify readiness

Check both systemd state and Velnor health:

```sh
systemctl is-active velnor-guardian.service velnor-daemon.service
velnorctl status --json
velnorctl get runners --output wide
velnorctl get slots --output wide
velnorctl doctor --url https://github.com/OWNER/REPO --name velnor --slots 1
```

An active PID alone is insufficient. Ready requires live control, a writable
journal, valid routing and runner-group state, a ready backend, and capacity.
Confirm the runner is online in GitHub before dispatching a workflow.

Run backend checks with the same paths used by the service:

```sh
velnorctl preflight \
  --config-dir /etc/velnor \
  --work-dir /var/lib/velnor/work
```

If Docker sees the work directory at another path, add
`--docker-host-work-dir PATH`.

For Docker Rust jobs, the job image's Mr Boxington installation should report
healthy from inside a job container:

```sh
mbx doctor
```

Its container store is `/var/cache/mbx` (managed targets are below
`/var/cache/mbx/targets`). With packaged storage, host stores are below
`/var/cache/velnor/v1/TRUST_SCOPE/compiler/mbx/REPOSITORY_ID`. Common trust
scopes include `untrusted`, `trusted`, and `release`; same-repository pull
requests on a trusted pool use `pr`, and custom pools keep their configured
scope. An invalid repository ID uses job-ephemeral storage instead. Do not
merge trust-scope or repository directories while diagnosing disk use. Mr
Boxington's internal 20 GiB cache, 30 GiB target, and 50 GiB combined GC
limits remain subject to Velnor's host disk accounting. Cargo registry and
Git source caches are independent and must be inspected separately.

Jobs run unbounded: no per-job CPU/RAM ceiling is imposed anywhere. The
`max_jobs=N` permit ledger sets the shared host-wide concurrency ceiling, while
native slot count can limit that lane below `N`. If no explicit positive value
is set, the first daemon configures an unset ledger from its own slot count;
later daemons adopt that value rather than adding their slots. The Scale Set
adapter's TOML has no per-set capacity field. Velnor currently sends
`N.saturating_sub(occupied)` through `X-ScaleSetMaxCapacity`, capped at
`2,147,483,647` for its signed 32-bit header, or `0` before the ledger is ready
to advertise. This is Velnor-local behavior and an unverified deviation from
the upstream listener's configured total-capacity meaning; GitHub's handling
of the free-permit estimate is not established. Velnor uses GitHub's
assigned-job statistics to reconcile its local runner population. For an
under-parallelized build, check ready lane capacity, the tool's own parallelism
settings, and the host's actual load:
[Storage and resource budgets](/operations/storage-and-resources).

## Daily inspection

The read-only control socket exposes resource queries, bounded event watches,
logs, and telemetry:

```sh
velnorctl get hosts
velnorctl get instances
velnorctl get runners --output wide
velnorctl get slots --output wide
velnorctl get jobs
velnorctl get runs
velnorctl get queue
velnorctl events --limit 100
velnorctl logs JOB_UID_OR_RUN_ID --tail 200
velnorctl telemetry --limit 100
velnorctl top host
velnorctl wait instance/default --for Ready --timeout 60
```

`top` requires a target: `host`, `instances`, `slots`, `jobs`, or `storage`.
Logs, events, and telemetry are bounded; expired cursors require a fresh
snapshot. There is no Prometheus endpoint, dashboard, SSE endpoint, or HTTP
health endpoint.

Workflow-run reads are:

```sh
velnorctl run list
velnorctl run view RUN_ID
velnorctl run watch RUN_ID
velnorctl run logs RUN_ID
```

Local status reports stored identity, labels, V2 state, and credential
presence. It is not a systemd liveness check:

```sh
velnorctl status --json --config-dir /etc/velnor --state-dir /var/lib/velnor
```

## Files and sockets

The packaged defaults are:

```text
/etc/velnor/velnor.env
/etc/velnor/secrets.env
/etc/velnor/execution.toml
/var/lib/velnor/state.db
/var/lib/velnor/work
/run/velnor/<instance>/control.sock
/run/velnor/<instance>/admin.sock
```

The control socket serves reads. The admin socket is reserved for lifecycle
mutations, but mutation support is currently disabled: `/v1/info` advertises
`mutations: false`, and lifecycle POSTs return unsupported/501. No documented
operator command currently changes fleet state through that socket. Do not
describe it as a working lifecycle API.

Control sockets are protected by Unix peer permissions. The read socket uses
the `velnor` group; the admin socket uses `velnor-admin`. Root and the socket
owner are also authorized.

Configuration resolution is, in order: explicit `--config-dir`,
`VELNOR_CONFIG_DIR`, systemd state directory, `VELNOR_STORAGE_ROOT`, then XDG
state. Runner configuration is stored as `runner.json` with a private
directory and file permissions. The resolver does not use `$HOME/.velnor`.

## Service lifecycle

Inspect services and recent logs:

```sh
systemctl status velnor-daemon.service
journalctl -u velnor-daemon.service -b --no-pager
systemctl list-timers 'velnor-doctor*'
```

systemd restarts the daemon after its process exits. Errors the daemon handles
retry in-process and do not trigger a systemd restart while it remains alive.
The doctor is a periodic oneshot; `loaded inactive dead` after it completes is
normal. Inspect its timer and failed-unit state instead of treating the
completed probe as a dead daemon.

After configuration changes, restart the exact affected daemon:

```sh
sudo systemctl restart velnor-daemon.service
```

On SIGTERM, idle slots deregister and exit, while active jobs continue. The
controller stops idle slots and waiters, preserves active job workers, waits
for graceful completion, and escalates if the stop timeout is exceeded. The
default daemon unit allows active jobs up to three hours before systemd kills
the remaining cgroup.

## Upgrade and release control

Before an upgrade, enumerate all `velnor*.service` units and stop every active
fleet service. Controller and slot instances are separate systemd units, and an
older install may leave legacy `velnor-job@…` instances active. Stopping only
the daemon and guardian does not stop these units. Stop every active service
reported by the listing, including legacy job instances. The package check
requires fleet services to be inactive or failed. It exempts lock-serialized
maintenance `Type=oneshot` services and their timers, which may remain enabled.
Then hold the exclusive transaction lock for the whole package operation:

```sh
sudo systemctl list-units --type=service --all --no-legend --plain 'velnor*.service'
sudo systemctl stop \
  velnor-daemon.service velnor-daemon@NAME.service velnor-guardian.service \
  velnor-controller@NAME.service velnor-slot@SLOT.service \
  velnor-job@NAME.service
sudo systemctl list-units --type=service --all --no-legend --plain 'velnor*.service'
sudo /usr/bin/flock --exclusive --nonblock --no-fork \
  /run/velnor/package-transaction.lock \
  apt-get install ./velnor-runner-VERSION-ARCH.deb
```

Repeat the stop command for every listed active daemon, controller, slot, and
legacy job instance. Verify that no fleet service is active; the package check also
rejects other active Velnor units unless they are lock-serialized maintenance
oneshots or their timers.

Every shipped Velnor service takes the shared lock. Scheduled maintenance
timers (`velnor-doctor*.timer`, `velnor-cache-gc.timer`,
`velnor-fleet-policy-audit.timer`) may stay enabled: their `Type=oneshot`
services are serialised by that lock, so a run that fires mid-transaction waits
for the transaction and then executes the new binary. Package hooks reject
direct or unlocked configuration and do not restart or re-enable fleet
services; the only unit the package enables itself is `velnor-cache-gc.timer`
(mask it to opt out).

### Owned-worker marker format change

The runner now writes structured process-identity and launch-token records in
`owned/{isolation_id}.{generation}`. Earlier releases wrote only a decimal PID.
The new reader rejects decimal markers, and old readers cannot safely interpret
the new records. Do not run old and new controllers or workers together.

Before crossing this format change:

1. Stop new work in every Native and Scale Set scope. Let active jobs reach
   terminal completion and owned cleanup while the old release still runs.
2. Enumerate all Velnor service units and stop every active fleet service,
   including the default and named daemons, guardian, and each independently
   managed `velnor-controller@` and `velnor-slot@` instance. If present, also
   stop legacy `velnor-job@…` instances from older installs. These worker units
   can remain active after daemon and guardian stop. The
   package pre-install check requires fleet services to be inactive or failed;
   it exempts lock-serialized maintenance oneshots and their timers. Never
   signal a process using only the PID in an old marker; PIDs can be reused.

   ```sh
   sudo systemctl list-units --type=service --all --no-legend --plain 'velnor*.service'
   sudo systemctl stop \
     velnor-daemon.service velnor-guardian.service velnor-daemon@NAME.service \
     velnor-controller@SCOPE.service velnor-slot@SLOT.service
   sudo systemctl list-units --type=service --all --no-legend --plain 'velnor*.service'
   ```

   Repeat the stop command for every listed fleet service instance. Verify
   each fleet service's `ACTIVE` state is `inactive` or `failed`.
3. With all fleet writers stopped, take a consistent backup of the permit ledger,
   every configured demand/state database, and the slot state directories,
   including their journals and marker files.
4. Inventory remaining decimal files under each state root's `owned/`
   directory. Match each exact isolation ID and generation to its slot journal,
   in-flight record, worker registry, and GitHub Run Service state. If an
   attempt is active or uncertain, stop the upgrade, start only the old cohort,
   let it resolve the attempt, then repeat the drain and stop steps. Remove an
   exact stale marker only after durable terminal/cleanup evidence and absence
   of its owning service cgroup are both established; archive the original
   bytes first. Never convert a PID-only marker into a structured marker or
   infer ownership/death from that PID alone. If evidence is incomplete, leave
   the marker and keep the new release stopped.
5. Install the new release and start the complete daemon cohort together.
   Check service logs for marker or permit-readiness errors before restoring
   traffic.

Rollback is also a drained operation. A new release can write marker and
journal data that an old binary cannot read. Stop every new controller and
worker, then restore the full pre-upgrade state backup and matching old package
as one set. Do not downgrade only the executable while retaining new-format
state; any state written after the backup must be reconciled separately.

Release commands are provided by `velnor-runner`:

```sh
sudo velnor-runner release verify-installed
sudo velnor-runner release activate --record RELEASE_RECORD.json
sudo velnor-runner release rollback
sudo velnor-runner release export
```

`verify-installed` is also run before daemon startup and rejects an absent or
mixed binary, package, or manifest tuple. `velnorctl release` is not an
available command.

Preview-channel packages carry their own identity, so a preview deb is
startable without the stable release chain: each deb ships
`/usr/share/velnor/package-record.json`, and activation reads it directly.

```sh
sudo velnor-runner release activate --record /usr/share/velnor/package-record.json
```

A stable release never activates from the package record inside its own deb;
it still requires the out-of-band release record published with the release.

After activation or upgrade, verify the installed tuple, then start services:

```sh
sudo velnor-runner release verify-installed
sudo systemctl enable --now velnor-guardian.service
sudo systemctl enable --now velnor-daemon.service
sudo systemctl enable --now velnor-doctor.timer
```

## Commands that do not mutate state

These CLI shapes are accepted but currently return unavailable, unsupported,
or planned results. They do not change hosts, runners, or GitHub:

```text
velnorctl cordon|uncordon|drain|resume|restart|recycle instance/NAME ...
velnorctl scale instance/NAME --slots N ...
velnorctl reconcile runners --dry-run
velnorctl run cancel|rerun|download|dispatch|open ...
velnorctl diagnostics bundle --archive PATH
velnorctl storage du|gc|history|reservations|leases|explain-pressure ...
```

`velnorctl storage paths` and `velnorctl storage status` are read-only local
inspection commands. `velnorctl cache gc` can delete cache data only when the
required confirmation and lease checks succeed; treat force-bypass options as
emergency operations.

## First failure checks

1. Check the daemon unit, boot journal, and doctor timer.
2. If token errors appear, fix the matching secrets file; supervised retries
   continue automatically.
3. If the control API is unavailable, verify the selected instance/context,
   socket paths, and Unix group membership.
4. If registration never starts, run `velnorctl preflight` with the service's
   config and work paths. Backend, Docker/Buildx, KVM, and bind-visibility
   failures are fail-closed.
5. If GitHub queues work but Velnor sees no job, verify runner labels, scope,
   runner-group policy, online state, and `velnorctl get runners`/`get queue`.
6. If Velnor executes but GitHub lacks logs or completion, inspect
   `velnorctl events`, `velnorctl logs JOB_UID_OR_RUN_ID`, telemetry, and the daemon
   journal. Completion is retried and local outbox state is retained until
   remote acknowledgement or terminal observation.

For lifecycle-stage diagnosis, see [Troubleshooting](/troubleshooting).
