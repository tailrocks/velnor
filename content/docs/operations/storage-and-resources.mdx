# Storage and resource budgets

Velnor derives what a job may use from what the machine actually has, rather
than letting each tool assume it owns the host. Jobs run unbounded — no
CPU/RAM ceiling is imposed on any container, daemon, or compiler — and host
capacity is governed by a single `max_jobs=N` permit ledger. This page
describes the store catalog, the unbounded execution policy, and how disk
pressure is handled.

## The store catalog

Every persistent store Velnor owns has exactly one path expression, published
in one catalog. Writers and both garbage collectors resolve through it, so a
store cannot be written at one path and reclaimed at another.

| Class | Contents | Reclaimable |
| --- | --- | --- |
| `cargo` | Cargo registry cache, registry index, Git database, and `$CARGO_HOME/bin` | yes |
| `mise` | mise download cache, tool installs, and per-version binaries | yes |
| `targets` | Host-persistent Cargo target generations | yes |
| `actions-cache` | `actions/cache` storage | yes |
| `artifacts` | Local artifact store, bucketed per workflow run | yes |
| `mbx` | Mr Boxington cache and managed targets | yes |
| `sccache` | Explicit `sccache-action` store | yes |
| `gha-cache` | Hosted GitHub Actions cache service storage | yes |
| `docker` | Docker's own image, container, volume, and build storage | no |

Each reclaimable class declares a lease class a running job publishes to mark
the store live, so a reclaimer cannot delete a class it does not own, and
cannot delete a store a job is using. `docker` declares none: Velnor never
reclaims Docker's storage by scope, but host disk accounting must include it,
because it consumes the same filesystem.

Stores resolve under `VELNOR_STORAGE_ROOT` when set, otherwise through the
systemd state directory and XDG defaults documented in
[Configuration](/reference/configuration). The daemon-shared work root holds
cross-slot warm data; slot-scoped paths (mbx object/target trees, mise
installs, stable workspaces) lift to that root by construction so affinity
matters but the catalog stays singular.

| Store | Shared across slots | Scoped by |
| --- | --- | --- |
| Cargo registry cache/index + git db | yes (trust scope) | repository id |
| mise download cache | yes (trust scope) | repository id |
| mise installs + per-version binaries | per slot | trust + repository |
| mbx cache + managed targets | per slot | trust + repository |
| actions-cache / gha-cache emulator | per host | repository + key |
| artifacts | per run | workflow run id |

Operator GC for reclaimable Velnor-owned classes is
`velnorctl cache --work-dir DIR gc --yes`, typically on a systemd timer after
baseline measurement with
`velnorctl cache du`. That reclaims UUID workspaces and orphaned images under
the 2 GiB admission floor; it does not delete live leases. BuildKit and Docker
image storage remain operator-managed on trusted docker hosts.

## Unbounded execution and the host permit ledger

Jobs run unbounded. No Docker `--cpus`/`--memory`/cpuset flag, no
`velnor-jobs.slice` CPU/RAM ceiling, and no compiler partition
(`CARGO_BUILD_JOBS`, `MAKEFLAGS`, `MBX_SCHEDULER_*`) is ever imposed:
every container sees the whole machine, and builders size themselves.
Workflow `container.options` quota flags are stripped at admission and
again at emission; nested creates through the job lease proxy are
stripped the same way. `velnor-jobs.slice` exists for identity and
cleanup ancestry only.

Host capacity is governed instead by a single host-wide `max_jobs=N`
permit ledger, shared by the native and Scale Set lanes. One top-level
job holds one permit from acquisition-commit until terminal work and
owned cleanup are confirmed; a full ledger skips the acquisition and
the broker redelivers. The only number to tune for completed-work
throughput is `N` (`--max-jobs` / `VELNOR_MAX_JOBS`, defaulting to the
daemon's slot count on single-daemon hosts). The first daemon start
configures `N`; later starts adopt the configured value, so a second
scope daemon's slot count never rewrites host capacity — an explicit
`--max-jobs` always wins as deliberate intent.

Native offers queue oldest-observed-first across every scope: each broker
offer is recorded with an immutable first-seen age, redelivery retains
the original age, and a younger offer defers while older eligible demand
exists that free permits cannot also cover. Ordering is advisory and
bounded by freshness; `occupied <= N` is enforced atomically by the
ledger behind it. No global FIFO is promised: GitHub controls delivery
order.

## Mr Boxington store limits

On the Docker backend the Mr Boxington store is mounted at `/var/cache/mbx`
with managed targets below `/var/cache/mbx/targets`. Mr Boxington owns garbage
collection inside it; Velnor supplies the limits:

```text
MBX_GC_AUTO=true
MBX_GC_MAX_SIZE=20GiB
MBX_GC_INCREMENTAL_MAX_SIZE=20GiB
MBX_GC_INCREMENTAL_MAX_AGE=30d
MBX_TARGET_MAX_SIZE=30GiB
MBX_GC_MAX_TOTAL_SIZE=50GiB
```

These operate inside Velnor's host disk accounting; they do not increase host
capacity. Cargo registry and Git source persistence are separate stores and are
unaffected by Mr Boxington's GC. The combined 50 GiB cap applies **per slot**
mbx directory (`MBX_GC_MAX_TOTAL_SIZE`), not once for the whole host.

## GitHub lane cache budget (separate)

The GitHub lane uses the platform `actions/cache` service, not Velnor host
stores. Generated maintenance enforces an internal **8 GiB** class table under
the platform's default **10 GB** repository cap; idle entries are evicted after
**seven days** regardless of Velnor policy. Producers on the default branch
refresh trusted snapshots; consumers on pull requests restore only. Prefix
restore (matched restore-key, primary key miss) is an expected warm path, not
a failure. Do not raise `VELNOR_MAX_JOBS` when GitHub entries are cold—the
lanes are independent.

## Disk pressure

Free space is measured with `statvfs` on the filesystem that actually holds the
work root, using the unprivileged figure (`f_bavail`), not the root-reserved
one. Docker's own usage is measured and subtracted from the headroom Velnor is
willing to promise; when it cannot be measured it is treated as unknown, never
as zero.

The free-space floor is 2 GiB. Below it, a slot must not admit a job. Pressure
is handled as a total state machine — every state has a defined successor and
none of them means "sleep and try again forever":

| State | Meaning | Action |
| --- | --- | --- |
| `Healthy` | at or above the floor | admit jobs |
| `Reclaiming` | below the floor, reclaim not yet attempted this episode | run the bounded reclaimer, re-evaluate |
| `Degraded` | reclaim ran, still below the floor | refuse admission, with the time left before escalation |
| `Draining` | the degraded deadline expired | stop accepting work, shed the slot |
| `Deregistered` | terminal | delete the registration and exit |

The degraded deadline is 10 minutes and the drain deadline a further 5. Any
non-terminal state returns to `Healthy` the moment space appears; recovery is
checked before escalation. `Deregistered` is terminal and requires an operator
or the fleet controller to act.

Admission is evaluated *before* a job is acquired. Acquiring first and
discovering afterwards that the host cannot hold the job is what produced
doomed jobs and the indefinite park.

What a node does today when it is below the floor is measure, run the bounded
reclaimer, re-measure, and — if it is still below the floor — refuse readiness
with a `low disk space` reason naming the free and required bytes. That is
bounded and fail-closed. The escalation past `Degraded` into `Draining` and
`Deregistered` is defined but is not yet driven from the slot loop, so a host
that stays full holds a refusing slot instead of shedding it.

The reclaimer is bounded: it takes a leader lock so two daemons do not reclaim
concurrently, targets a byte goal rather than running to completion, skips any
class a live lease covers, and reports what it freed. It reclaims UUID job
workspaces and dangling untagged images; warm caches, volumes, builders, and
shared microVM work roots are protected or skipped. It does not scrub bytes.

`velnorctl storage paths` and `velnorctl storage status` report the resolved
roots and the per-class byte totals. `velnorctl storage explain-pressure` is
not available.
