# Plan 2026-09-14: native Engine API slice 3 — idempotent lifecycle mutations (GOAL 17/58)

Base: origin/main tip 5b4dfa54 at fetch time. Branch: r0-engine-api-3.
Worktree: /tmp/velnor-eng3. Follows slices 1-2 (#743 plus #750
corrections, #774).

## Problem

Slices 1-2 routed the read-only queries; every lifecycle mutation still
pays one `docker` subprocess, and the mutations have no typed facade
home — start/stop/remove argv is built ad hoc at each call site
(buildkit host ops, executor teardown, reclaim paths) with tolerance
logic copied per path. This slice adds the third Engine-API leg:
container start, stop (with timeout), and remove (with force/volume
options) through `docker/engine.rs`, each idempotent and
conflict-tolerant.

## Fix (this branch, strict scope)

Three new engine endpoints plus three new typed facade methods with the
slice-1 contract — API first under `min(class deadline, 5s)`,
historical CLI on ANY API failure, taxonomy preserved, deadlines plus
cancellation plus fallible runtime plus current-thread offload reused
from `engine_or_cli`, telemetry on fallback:

- `container_start(name)` — `POST /containers/{id}/start`;
- `container_stop(name, timeout)` — `POST /containers/{id}/stop[?t=N]`,
  the `-t` value verbatim, omitted when `None` so the daemon default
  applies exactly as the CLI does without `-t`;
- `container_remove(name, force, volumes)` — `DELETE
  /containers/{id}[?force=1][&v=1]`.

Idempotent status mapping (all proven live on Engine 29.4.0): 2xx acts;
304 is already-started/already-stopped success; 404 on remove is
already-removed success; every other status (404 on start/stop, 409,
5xx) is an API error the CLI fallback re-derives. The mutations are
safe under fallback-after-timeout because they are idempotent: a
response lost after the daemon acted is re-driven by the CLI leg and
converges (re-removing a gone container reads as already-removed on
both legs). Non-idempotent mutations (create, run) are excluded by
this argument, not by taste — a fallback after an ambiguous timeout
could act twice.

Genuine conflicts surface typed Conflict on both legs: start/stop on a
missing container re-derives `NotFound` (Conflict-shaped: another
writer removed the object mid-flight), and removing a running
container without force re-derives `DockerCommandError` with
`DockerErrorCategory::Conflict` (the daemon's 409 sentence, shared by
both transports). The in-progress removal sentence stays tolerated
success on both legs; a stderr that also matches Transient surfaces
instead of masking. One vocabulary needle added for the 409 sentence
(`cannot remove`): the three categories are unchanged, and no retry
behavior changes — rm failures never reach the start retry decision —
only the reported category for that sentence moves Terminal to
Conflict, with the one test pinning it updated.

Two honest divergences, both documented in code and pinned by test.
First, the already-bit on start/stop is exact on API (204 vs 304) but
conservative on CLI: `docker start`/`stop` print the name identically
for fresh and redundant ops, so the CLI leg reports acted on any exit
0. Distinguishing would cost an inspect plus a TOCTOU race to save
nothing — both succeed, which is the idempotence contract. Remove
agrees exactly (404 maps to already-removed on both legs). Second, the
facade CLI legs separate the operand with `--` where the migrated
host call sites did not; behavior is identical (proven live) and the
classification/deadlines are unchanged.

Consumer migration (one per method, host path, behavior-preserving):
`buildkit::stop_builder_daemon`, `buildkit::start_builder_daemon`, and
the container half of `buildkit::remove_builder` now run through the
facade. The volume half stays CLI (volume remove is out of scope), as
do the executor teardown and reclaim rm paths — teardown's exit-124
tolerance (success there, typed timeout everywhere else) stays at its
owned call site for a later slice to decide.

Out of this slice, deliberately: executor teardown/reclaim rm
migration, volume/network remove, create/run (non-idempotent, unsafe
under fallback), connection reuse, consecutive-failure short-circuit.

## Live findings (OrbStack Engine 29.4.0 / API 1.54)

Shell probes (no committed live test; all probe objects deleted, 0
containers and 0 volumes remaining) fixed the truth table both legs
implement:

- API: start on running → 304 empty; start on created → 204 empty;
  stop on stopped → 304; stop on running → 204; DELETE stopped →
  204; DELETE missing → 404 + `{"message":"No such container: X"}`;
  DELETE running w/o force → 409 + the `cannot remove ... container
  is running` document; DELETE running `?force=1` → 204.
- CLI: start/stop print the name and exit 0 whether fresh or
  redundant; start on missing answers TWO lines (`No such container`
  plus `failed to start containers`); rm on missing exits 1 with the
  same `No such container` sentence the API 404 carries; `--time` is
  deprecated in favor of `-t` (facade uses `-t`); `--volumes` long
  form verified; named volumes survive `--volumes` on both
  transports.

## Numbers

Subprocess count, start/stop/remove cycle (committed regression test
`lifecycle_cycle_is_identical_with_zero_subprocess_on_api`):

- before (engine off): 3 mutations = 3 `docker` subprocesses;
- after (engine on): 0 runner calls, identical typed outcomes.

Representative-job projection: the migrated consumers are
maintenance/horizon paths (builder stop/restart/delete), not the
per-job hot path, so this slice eliminates ~0 per representative job
and up to 3 per maintenance pass that acts on a builder daemon. The
per-job win waits on the teardown rm migration (follow-up), which
this slice's contract and tests are shaped for.

Latency, live start+stop(`-t 0`)+rm cycle, 10 iterations per leg,
macOS arm64 via OrbStack socket (shell-measured, loaded machine):

- CLI p50 1038ms vs API p50 728ms — ~1.4x.

Mutations are daemon-work-dominated (cgroup setup, SIGKILL, unmount),
so unlike the memory-served queries (35-40x) the latency win is only
the ~80ms spawn overhead per call — consistent with slices 1-2. The
win here is process count (3→0), not latency.
