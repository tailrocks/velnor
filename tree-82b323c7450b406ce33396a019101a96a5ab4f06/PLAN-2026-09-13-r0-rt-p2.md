## P2-1: DockerLifecycleGuard parks peers invisibly

`capacity.rs::lock_with_concurrency` polled every 25ms with no deadline and
no telemetry, so simultaneous teardowns could park behind a stuck slot
holder forever with nothing in the log.

Fix (`crates/velnor-runner/src/capacity.rs`,
`crates/velnor-runner/src/executor.rs`):

- Acquire bound: `VELNOR_DOCKER_LIFECYCLE_WAIT_SECS` (default 120s, floor
  1s). Past the bound the guard degrades — the caller proceeds without a
  host-wide slot — instead of parking teardown behind a stuck peer.
- Stage telemetry: `lock_for_stage` names the stage
  (`cleanup`, `cleanup-services`, `create-network`, `start-job`, …);
  acquires waiting ≥1s and every degrade emit a
  `forensics.docker_lifecycle` stderr line with stage, waited_ms, slots.
- Regression test:
  `docker_lifecycle_guard_degrades_past_the_bound_instead_of_parking`
  (zero bound ⇒ deterministic, no sleep timing).

## P2-2: StepLog mirror clone-per-chunk + scan under std Mutex

The async step-log publisher did `push(log.clone())` under a
`std::sync::Mutex` per chunk: a full `StepLog` clone plus a linear
byte-scan (and eviction rescans) on a tokio worker, ~2x memory.

Fix (`crates/velnor-runner/src/runner.rs`):

- Move semantics: each received `StepLog` moves into one `Arc`; the mirror
  takes an `Arc` bump, the publisher keeps the same `Arc` for masking and
  upload (`ProcessedStepLog.log` is now `Arc<StepLog>`).
- Byte sizes computed BEFORE locking and stored per record, so eviction
  subtracts instead of rescanning. Critical section is an Arc bump plus
  integer math — no clone, scan, or syscall — which is why the `std` mutex
  stays correct (documented on the struct).
- `take_logs` (cancel path, post-drain) unwraps the last `Arc` without
  cloning; the clone arm is a cold fallback.
- Regression test:
  `streamed_step_log_mirror_shares_records_without_cloning_payload`
  pins the `strong_count == 2` sharing contract and move-out take.

## P2-3: spawned_children leaks + kill(1) fallback

`ProcessCommandRunner::kill` did `remove` → `kill()?` → `wait()`: a kill
failure (already-exited child) skipped `wait` and leaked a zombie; the
unknown-pid fallback fork+exec'd `kill(1)` per signal; a pid-key
collision silently dropped a live `Child` without reaping.

Fix (`crates/velnor-runner/src/executor.rs`):

- Kill path always waits: `let _ = child.kill(); child.wait()?`. Entry is
  dropped up front, so a retry falls through to the signal path.
- Unknown-pid fallback is now direct `rustix::process::kill_process`
  (`SIGTERM`), no subprocess. ESRCH ⇒ Ok (already gone), matching the
  cancel ladder — this also lets a `stop_jailer` retry converge instead of
  erroring forever.
- Spawn reaps a stale entry on pid-key collision via
  `reap_spawned_child` (SIGKILL + wait, loud on failure).
- Regression test: `kill_reaps_drops_the_entry_and_treats_gone_as_gone`
  (real `sh -c "exec sleep 30"`: entry dropped, `kill(pid,0)` ⇒ ESRCH
  proving reap-not-zombie, double-kill Ok, impossible-pid Ok).
