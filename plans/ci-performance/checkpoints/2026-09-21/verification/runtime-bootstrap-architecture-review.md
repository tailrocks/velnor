# Runtime bootstrap architecture review

**Verdict:** The old-pin → immutable runtime → successor pin-and-regenerate sequence avoids a policy/runtime cycle, but the current source-only PR cannot pass the existing regeneration gate when its renderer changes output. The publisher also needs a successful main-CI result for the exact source SHA before publishing.

## Findings

1. **The source-only stage conflicts with the regeneration gate.** The tracked Rust generator unit runs `mbx run --locked --manifest-path Cargo.toml -- --plain --check ../..` from `crates/velnor-workflow` ([project.toml:332](/Users/donbeave/Projects/work/velnor/.github/ci/project.toml:332)); the `.github-gen` regen gate repeats that command ([velnor-workflow.toml:222](/Users/donbeave/Projects/work/velnor/.github-gen/velnor-workflow.toml:222)). This checks the PR’s current crate source against the checked-in generated tree. If source changes renderer output while the source-only PR retains the old tree, this check fails.

   The policy path does not suppress the unit check. With the old declared pin, `policy_candidate_step` checks the old tree using the base runtime and exits on a match ([s2/mod.rs:4688](/Users/donbeave/Projects/work/velnor/crates/velnor-workflow/src/s2/mod.rs:4688)). That correctly avoids a candidate lookup for this phase, but it is a separate gate. Candidate packaging runs after unit commands ([primitives/ir.rs:2176](/Users/donbeave/Projects/work/velnor/crates/velnor-workflow/src/primitives/ir.rs:2176)), so the failed source check also prevents that candidate from being packaged.

   The CLI confirms this order: `run` renders from the current checkout and calls `write_generated_with_options(..., cli.check, ...)` before the later D19 `verify_declared_pin_renders_tree` check ([s2/mod.rs:5677](/Users/donbeave/Projects/work/velnor/crates/velnor-workflow/src/s2/mod.rs:5677), [s2/mod.rs:5696](/Users/donbeave/Projects/work/velnor/crates/velnor-workflow/src/s2/mod.rs:5696)). The pinned runtime environment only serves that later pin check; it cannot make the initial current-source render match an old generated tree.

   PR 979 as submitted has the inverse problem: it changes generated `ci-main.yml` and `ci-pr.yml` output but leaves the declared pin at `38dbf85…` (`ci-main.yml:66,154,162`; `ci-pr.yml:65`). Mainline policy rejects a tree that matches the candidate renderer rather than the declared pin ([policy.rs:463](/Users/donbeave/Projects/work/velnor/crates/velnor-workflow/src/policy.rs:463)). Merging that PR as-is cannot leave main Policy green; generated output must follow the staged pin adoption.

   **Required adjustment:** Give the source-only phase a narrow check proving that tracked output still matches the old declared pin, and test the changed source separately (renderer tests or a scratch render). Keep the normal source-render check for the successor PR that updates the pin and generated files atomically. Do not disable candidate tests globally.

2. **The runtime publisher can publish a SHA whose main CI fails.** The product workflow runs on every `main` push and manual dispatch ([ci-runtime-products.yml:22](/Users/donbeave/Projects/work/velnor/.github/workflows/ci-runtime-products.yml:22)). Its jobs are `closure → build → publish`, with no dependency on `ci-main` or `ci-required` ([ci-runtime-products.yml:36](/Users/donbeave/Projects/work/velnor/.github/workflows/ci-runtime-products.yml:36), [ci-runtime-products.yml:90](/Users/donbeave/Projects/work/velnor/.github/workflows/ci-runtime-products.yml:90), [ci-runtime-products.yml:201](/Users/donbeave/Projects/work/velnor/.github/workflows/ci-runtime-products.yml:201)). It proves closure/revision, artifact digests, provenance, manifest shape, and consumer installation smoke behavior, but it does not run generator tests or regeneration checks ([ci-runtime-products.yml:167](/Users/donbeave/Projects/work/velnor/.github/workflows/ci-runtime-products.yml:167), [ci-runtime-products.yml:230](/Users/donbeave/Projects/work/velnor/.github/workflows/ci-runtime-products.yml:230)). Manual dispatch is also an ungated path.

   **Required adjustment:** Publish only after a successful `ci-main` completion from this repository’s `main` push. Verify workflow identity, event, branch, repository, conclusion, and completed run SHA; build and stamp that exact SHA. Remove manual publication or require it to prove the same successful run. Keep the publisher independent of PR candidate artifacts. Stage 0 then checks the old pin/tree without waiting on the new product; after main CI succeeds, the publisher creates the immutable product; the successor pin-and-regenerate PR consumes it.

3. **Strict pin-only policy needs declared-product acquisition on the adoption PR.** `policy.rs` already fails `TreeComparison::Candidate` on mainline ([policy.rs:463](/Users/donbeave/Projects/work/velnor/crates/velnor-workflow/src/policy.rs:463)). If policy is strengthened to reject Candidate on PRs too, a valid pin-and-regenerate PR must acquire the new declared pin’s immutable, attested product using the base-owned setup action before comparison. The current owner-policy job starts from the base `BASE_PIN` and its candidate path; without declared-pin acquisition, the old base renderer cannot reproduce the new pinned tree. The existing consumer `policy_renderer_steps` demonstrates the product-acquisition pattern ([s2/mod.rs:4779](/Users/donbeave/Projects/work/velnor/crates/velnor-workflow/src/s2/mod.rs:4779)). Use only the setup action checked out from the PR base, keep the policy job read-only, fail closed if the release is missing or its attestation/closure/revision fails, and require `TreeComparison::Pin`.

   Candidate packaging and its closure/manifest/tokenless-execution tests can remain in `ci-pr` as diagnostics. They must not authorize the tracked tree when policy requires a released pin. The source-only phase uses the unchanged old pin; the adoption PR runs after the main publisher has released the new pin, so this does not create a cycle.

I inspected the workflow templates, generated workflow contracts, candidate producer/consumer code, runtime product publisher, and policy comparison logic. I ran no tests, builds, or Git mutations.
