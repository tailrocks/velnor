## Problem

Review of merged #743 (`430364de`) found five gaps, all in the new
`docker/engine.rs` fast path and its facade routing:

1. Two panics where the design promises CLI fallback: `engine_runtime()`
   `.expect()`s the runtime build, panicking the job thread on a sick
   host; `block_in_place` panics when a current-thread runtime is current.
2. Ports-order skew: `parse_inspect_ports` sorts but `parse_port_mappings`
   preserves daemon order, and `service_context` is first-wins per
   container port — so the transports could pick different host ports.
3. Cancellation: the API wait races nothing, leaving up to 5 s
   unresponsive per query under cancel.
4. Latency evidence: the 743 probe was temporary (removed before the PR),
   so the numbers are not re-runnable.
5. Test honesty: no fixture proves CLI equals API on multi-port output in
   disagreeing order.

## Fix (this branch, strict scope)

- `engine.rs`: `engine_runtime()` returns `Option`, cached; a build
  failure routes to the CLI fallback (`EngineFaultKind::Runtime`), never
  panics. `block_on_engine` returns `Option`, takes `Send` futures, and
  checks `Handle::runtime_flavor()`: multi-thread keeps `block_in_place`,
  current-thread drives the future on the dedicated runtime from a
  scope-borrowed helper thread (a failed join is a fallback, never a
  panic). `FailRuntimeBuildGuard` simulates the build failure in tests.
- `client.rs` + `engine.rs`: one shared `sort_port_mappings` comparator,
  applied by both projections. Sorting both is the only honest unification:
  `serde_json` maps iterate sorted regardless of daemon key order, so the
  API leg cannot preserve encounter order.
- `engine.rs` + `client.rs`: every API attempt runs inside `cancel_race`,
  which selects the attempt against the active job's `JobCancellation`
  (10 ms poll; direct await with zero overhead when no token is active, as
  on the maintenance path). A cancelled wait falls back to the CLI — the
  same spawn-and-ladder-kill the CLI path always ran under cancel, so the
  taxonomy and the cancel shape are unchanged. New `EngineFaultKind::Cancelled`
  keeps the telemetry vocabulary closed. The cancel/restore unit test takes
  the metrics serial lock so its briefly installed cancelled token cannot
  flake a concurrent routing test's script.
- `client.rs` tests: the latency probe is committed as the ignored
  `live_engine_latency_bench` (daemon-cgroup query, needs no container;
  skips honestly without a live socket; asserts API==CLI per iteration and
  reports n/p50/p95/min/max per leg).
- `engine.rs` tests: live-captured multi-port fixture (`docker create
  -p 9090 -p 10000`, Engine 29.4.0, both documents verbatim) asserting
  `parse_port_mappings` equals `parse_inspect_ports`. The capture proves
  the skew is real: the daemon prints `docker port` in numeric order (9090
  group first) while the Ports object arrives lexicographic (10000 first).

## Numbers

`live_engine_latency_bench`, daemon-cgroup query, 25 iterations per leg,
macOS arm64 (Darwin 25.6.0) via OrbStack Engine 29.4.0, box heavily loaded
(load avg ~40-50 — absolutes are load-inflated, the ratio is the signal):

- run 1: API p50 8.61 ms (p95 37.05, min 5.98, max 72.12) vs CLI p50
  134.03 ms (p95 449.17, min 81.44, max 536.57) — ~16x;
- run 2: API p50 6.44 ms (p95 21.02, min 5.33, max 36.80) vs CLI p50
  150.86 ms (p95 286.12, min 86.62, max 413.53) — ~23x.

Not comparable 1:1 with the 743 probe (~35-42x on container-inspect):
different query (`/info` is a larger document than one inspect) and much
higher box load. Per migrated call the shape holds: tens-to-hundreds of ms
of subprocess becomes single-digit ms of socket.
