# Plan 2026-09-14: native Engine API slice 2 — owned-list queries (GOAL 17/58)

Base: origin/main tip 545bab27 at fetch time. Branch: r0-engine-api-2.
Worktree: /tmp/velnor-eng2. Follows slice 1 (#743 plus #750 corrections).

## Problem

Slice 1 routed the seven single-object/daemon queries; every other
read-only query still pays one `docker` subprocess. The task menu for this
slice (network inspect/list, volume list/inspect, image list/history,
container top/stats, daemon events) does not exist as facade queries —
the facade holds only the seven routed plus the buildx pair, which has no
Engine equivalent. The queries that DO exist are the reclaim listings
(`ps` / `network ls` / `volume ls` builders in `docker_lease.rs`,
consumed as CLI text through injected closures), and of those exactly
three run on every job: terminal cleanup's
`ps` + `network ls` + `volume ls` at job end.

Negative inventory (verified by search, all Engine-unmappable or
callerless): `top`/`stats` appear only in the guest lease-proxy
allowlist and deadline classification; `events`/`history` only in
deadline classification; `docker images` only as a fault-injection
passthrough assertion; `network inspect` has one builder used solely
for error detail in the DNS-preflight failure path (routing it would
change error text); `volume inspect` has no call sites at all.

## Fix (this branch, strict scope)

Three new typed facade queries with the slice-1 contract — API first
under `min(class deadline, 5s)`, historical CLI on ANY API failure,
taxonomy preserved, deadlines plus cancellation plus fallible runtime
plus current-thread offload reused from `engine_or_cli`, telemetry on
fallback:

- `list_owned_containers(job_id)` — `GET
  /containers/json?all=1&filters={"label":["velnor.job-id=<job>"]}`,
  the same translation the CLI's `--filter label=` performs;
- `list_owned_networks(job_id)` — `GET /networks?filters=...`;
- `list_owned_volumes(job_id)` — `GET /volumes?filters=...`.

Identity rules, all proven live on Engine 29.4.0: `ps --format
{{.ID}}` and `network ls -q` print 12-char short ids, so the API legs
truncate full ids to 12 (pass-through when already short);
`{{.Names}}` renders slashless, so the projection strips the leading
`/` and comma-joins; `volume ls -q` prints `Name` verbatim. Empty
matches read as empty (`[]`, `{"Volumes":[]}` live; a null `Volumes`
is the same fact, not skew). The BuildKit-exclusion decision now owns
one typed-rows implementation both transports decide through, so the
rm argv cannot differ by transport.

Consumer migration: `docker_lease::reclaim_job_owned` (job-end
terminal cleanup, the only per-job listing consumer) splits into
`list_job_owned` (facade, Engine-routed) plus `remove_job_owned`
(CLI; removals are mutations, out of scope). Two phases where the old
closure version interleaved six calls: the borrow checker forces the
shape — one `&mut` runner cannot serve a live listing facade and a
removal closure at once — and terminal cleanup owns the job outright
(this path never revalidated between list and rm), so batching changes
no decision, only the call order. The executor call site runs the
phases sequentially through the same tolerant cleanup runner.

Out of this slice, deliberately: the retry/orphan/daemon-scoped
listings (key-exists and name filters are later `ListFilter`
variants), the job BuildKit cleanup pair, `system df` reporting,
single-object network inspect and version (still callerless — would
be dead code).

## Live findings (OrbStack Engine 29.4.0 / API 1.54)

A temporary live probe (removed before the PR, probe objects deleted)
asserted all three listings API==CLI on live labeled objects, 25
iterations per leg, twice — including end-to-end proof that the daemon
accepts the Rust-encoded `filters=` document and that short-id
truncation matches the CLI's rendering exactly. It caught one real
behavior the mock-first design assumed: `network ls -q` prints short
ids, not names (the old reclaim fixture said `guest-net`).

## Numbers

Subprocess count, owned-list sequence (committed regression test
`owned_list_sequence_is_identical_with_zero_subprocess_on_api`):

- before (engine off): 3 listings = 3 `docker` subprocesses;
- after (engine on): 0 runner calls, byte-identical typed values.

Representative-job projection (BC-7's 2-service job, 52-72
processes): job-end terminal reclaim drops its 3 listing subprocesses
(ps + network ls + volume ls); removals stay CLI by design. Combined
with slice 1's 10-14, the fast path now eliminates ~13-17 per job
(≈20-30%).

Latency, live 3-query owned-list sequence, 25 iterations per leg,
macOS arm64 via OrbStack socket:

- run 1: API p50 15.81ms vs CLI p50 199.84ms — ~12.6x;
- run 2: API p50 13.93ms vs CLI p50 236.30ms — ~17.0x.

Per listing: ~65-80ms of subprocess becomes ~5ms of socket.
