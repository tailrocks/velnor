# Storage and resource budgets

Velnor derives what a job may use from what the machine actually has, rather
than letting each tool assume it owns the host. Jobs run unbounded — no
CPU/RAM ceiling is imposed on any container, daemon, or compiler — and host
`max_jobs=N` caps concurrent admitted jobs; disk pressure separately gates
admission. This page describes the store catalog, the unbounded execution
policy, and how disk pressure is handled.

## The store catalog

Cache GC classes have one path expression in the shared store catalog. Their
writers and cache collectors resolve through it, so a store cannot be written
at one path and reclaimed at another. Stable workspaces live in per-slot work
roots outside the keyed cache namespace. Git mirrors live in their own class
under that namespace, appear in `storage status` and `cache du`, and use
separate locking and ref-retention rules. Cache GC applies its age and
overall-size policy, with per-repository leases protecting live use. Docker
storage is measured separately where available and is not reclaimed by
Velnor's cache catalog.

With packaged storage rooted at `/var`, trust-scoped classes use the sibling
namespace `/var/cache/velnor/v1__trust_scope_v1/trust-scope-v1-<digest>/`.
Repository and cache-key scoping varies by class; the matrix below gives each
class's current key, including `actions-cache`'s sanitized repository name.
The keyed layout does not migrate or reuse existing raw-scope paths under
`/var/cache/velnor/v1`. The Debian package's guarded `storage purge-legacy`
step removes supported old roots only for packaged instances still present in
the configuration. Undiscoverable custom roots, roots for deconfigured
instances, and unsupported old layouts may remain outside the keyed catalog
while consuming disk.

| Class | Contents | Reclaimable |
| --- | --- | --- |
| `cargo` | Cargo registry cache, registry index, Git database, and `$CARGO_HOME/bin` | yes |
| `mise` | mise download cache, tool installs, and per-version binaries | yes |
| `targets` | Retired host-persistent Cargo target generations; cataloged for cleanup, with no current writer | GC only |
| `actions-cache` (`caches` root) | Local `actions/cache` entries, Playwright browsers, Bun install cache, npm cache, and Terraform plugin cache | yes |
| `artifacts` | Local artifact store, bucketed by workflow run ID and attempt | yes |
| `mbx` | Mr Boxington cache and managed targets | yes |
| `sccache` | Explicit `sccache-action` store | yes |
| `gha-cache` | Velnor's local GitHub Actions cache service data | yes |
| `docker` | Docker's own image, container, volume, and build storage | no |

Running jobs publish `ScopeLease`s for the `actions-cache`, `artifacts`,
`cargo`, `mise`, `mbx`, and `sccache` classes. The GHA cache service instead
registers per-job token-to-identity sessions for request routing; these are
not `ScopeLease`s. The retired `targets` class has no current writer or active
lease and remains cataloged for cleanup only. `docker` has no Velnor scope
lease: its storage is measured separately where possible, but is not reclaimed
by class.

Canonical cache classes resolve below the configured cache root under the
keyed trust namespace, as documented in
[Configuration](/reference/configuration). Slot workers share that cache
root; some classes, such as MBX and mise installs, add per-slot subtrees.
Work roots are separate: each slot has its own job and stable-workspace paths,
while artifacts use a shared `<daemon-work-root>/_velnor_artifacts` root with
per-run buckets. Git mirrors also use separate locking and ref-retention
paths. Active non-MBX warm Cargo targets live inside per-slot
`stable-workspaces`, outside the store catalog, with a 30 GiB per-slot cap.
MBX keeps its own managed targets. The 200 GiB `VELNOR_BUDGET_TARGETS_BYTES`
default is a GC ceiling for residual entries in the retired `targets` class,
not a budget for active stable workspaces. The mise collector also scans
residual `mise/rustup` paths, but jobs set `RUSTUP_HOME=/root/.rustup`, so
current rustup toolchains are not written to that host store.

| Store | Shared across slots | Scoped by |
| --- | --- | --- |
| Cargo registry cache/index + git db | yes | trust scope |
| Cargo executable store (`$CARGO_HOME/bin`) | yes | trust scope + sanitized `github.repository` slug |
| mise download cache | yes | trust scope |
| mise installs | per-slot | trust scope + sanitized `github.repository` slug |
| mise per-version binaries | yes | trust scope + sanitized `github.repository` slug |
| `caches` root: `actions/cache`, Playwright, Bun, npm, Terraform plugin cache | yes | trust scope + sanitized `github.repository` slug; `actions/cache` adds its compatibility version and key |
| mbx cache + managed targets | per-slot subtrees | trust scope + numeric `github.repository_id` |
| sccache store | yes | trust scope + numeric `github.repository_id` |
| `gha-cache` service data | per host | repository, ref, optional normalized `base_ref`, and trust identity; then cache key |
| artifacts | per run | `GITHUB_RUN_ID-GITHUB_RUN_ATTEMPT` (`local-1` fallback) |
| Stable workspace | per-slot | admitted trust scope + numeric `github.repository_id` |

The `caches` root is one shared catalog class, accounted and reclaimed under
the `actions-cache` budget and lease. Cargo registry/Git downloads and mise
downloads are trust-scoped only; they do not add repository identity.

Routine GC for reclaimable Velnor-owned classes is
`velnorctl cache --work-dir DIR gc --yes`, typically on a systemd timer after
baseline measurement with `velnorctl cache du`. It may evict eligible,
unleased Velnor file-store entries under age and budget policy and remove
leftover workspaces. It leaves BuildKit cache and ordinary Docker images,
containers, and volumes alone.

On Docker-backend slots, 90% measured usage triggers cleanup of orphaned UUID
workspaces under work roots on that filesystem; this pass preserves file-store
and BuildKit caches. Below 2 GiB available, the emergency path may reclaim
eligible Velnor file-store entries and retry workspace cleanup. Liveness and
mount checks must pass. After each file-store reclaim, the runner samples free
space again. BuildKit pruning is considered only while that fresh sample stays
below the 2 GiB floor, and the pressure check repeats before each candidate
and prune. It requires an unclaimed current-domain builder, a native Linux
Docker Engine, and same-filesystem ownership checks.
Successful pruning stops the daemon but retains the builder and state volume.
With managed `cleanup: false`, the BuildKit post action releases its claim but
leaves the daemon running. A later horizon pass may stop the unclaimed daemon;
stopped builders with no holders are deleted after seven idle days. Pressure
reclaim does not prune dangling images or reclaim ordinary Docker images,
containers, or volumes by scope.

## Unbounded execution and the host permit ledger

Jobs run unbounded. No Docker `--cpus`/`--memory`/cpuset flag, no
`velnor-jobs.slice` CPU/RAM ceiling, and no compiler partition
(`CARGO_BUILD_JOBS`, `MAKEFLAGS`, `MBX_SCHEDULER_*`) is ever imposed:
every container sees the whole machine, and builders size themselves.
For Native jobs, workflow `container.options` quota flags are stripped at
admission and again at emission. User-supplied outer job/service volume,
host-mount, and socket options
(`-v`/`--volume`, `--mount`, `--volumes-from`, `--volume-driver`,
`--volume-opt`, and `--use-api-socket`) are also removed; runner-owned mounts
are constructed separately. Nested creates through the job lease proxy have
their own option filter. `velnor-jobs.slice` exists for identity and cleanup
ancestry only.

Concurrency is capped by one host-wide `max_jobs=N` permit ledger, shared by
the native and Scale Set lanes. Separately, disk pressure blocks admission
when a checked filesystem has less than 2 GiB available or is at least 90%
used, regardless of free permits. One top-level job holds one permit from
acquisition-commit until terminal work and owned cleanup are confirmed; a
full ledger skips the acquisition and the broker redelivers. `N` is the
concurrency knob (`--max-jobs` / `VELNOR_MAX_JOBS`, defaulting to the daemon's
slot count on single-daemon hosts), not a disk-pressure override. The first
daemon start configures `N`; later starts adopt the configured value, so a
second scope daemon's slot count never rewrites it — an explicit `--max-jobs`
always wins as deliberate intent.

Native offers queue oldest-observed-first across every scope: each broker
offer is recorded with an immutable first-seen age, redelivery retains
the original age, and a younger offer defers while older eligible demand
exists that free permits cannot also cover. Ordering is advisory and
bounded by freshness; `occupied <= N` is enforced atomically by the
ledger behind it. No global FIFO is promised: GitHub controls delivery
order.

## Mr Boxington store limits

On the Docker backend the Mr Boxington store is mounted at `/var/cache/mbx`
with managed targets below `/var/cache/mbx/targets`. Mr Boxington owns garbage
collection inside it; Velnor supplies the limits:

```text
MBX_GC_AUTO=true
MBX_GC_MAX_SIZE=20GiB
MBX_GC_INCREMENTAL_MAX_SIZE=20GiB
MBX_GC_INCREMENTAL_MAX_AGE=30d
MBX_TARGET_MAX_SIZE=30GiB
MBX_GC_MAX_TOTAL_SIZE=50GiB
```

These operate inside Velnor's host disk accounting; they do not increase host
capacity. Cargo registry and Git source persistence are separate stores and are
unaffected by Mr Boxington's GC. The combined 50 GiB cap applies **per slot**
mbx directory (`MBX_GC_MAX_TOTAL_SIZE`), not once for the whole host.

## GitHub lane cache budget (separate)

The GitHub lane uses the platform `actions/cache` service, not Velnor host
stores. Generated maintenance enforces an internal **8 GiB** class table under
the platform's default **10 GB** repository cap; idle entries are evicted after
**seven days** regardless of Velnor policy. Producers on the default branch
refresh trusted snapshots; consumers on pull requests restore only. Prefix
restore (matched restore-key, primary key miss) is an expected warm path, not
a failure. Do not raise `VELNOR_MAX_JOBS` when GitHub entries are cold—the
lanes are independent.

## Disk pressure

Free space is measured with `statvfs` on the filesystem that holds the work
root, using the unprivileged figure (`f_bavail`), not the root-reserved one.
Admission does not run `docker system df` or separately subtract Docker usage.
Docker bytes on that same filesystem already reduce `f_bavail`; Docker storage
on another filesystem is outside this measurement. `velnorctl cache du` can
report Docker usage separately when it can be measured.

Admission pressure begins when a checked filesystem has less than 2 GiB
available or reaches 90% used. On Docker-backend slots, 90% usage also
triggers cleanup of orphaned UUID job workspaces, leaving file stores and
BuildKit caches intact. Below 2 GiB available, the runner targets eligible
Velnor file-store entries and may prune an unclaimed current-domain BuildKit
cache.

The controller and each worker probe two roots: the effective config root
(`exec.config_dir`, falling back to the service state directory) and the
effective work root (configured `work_dir`, otherwise `<config-root>/_work`).
Exact duplicate paths are checked once. Paths on the same filesystem share one
sample using the lower available-space reading; each distinct filesystem has
its own pressure episode. An unmeasurable root blocks slot permits and job
admission.

An episode is keyed by the canonical service state directory and the Unix
device identity `unix-device:<st_dev hex>`. This is a device number, not a
filesystem UUID. Its identity and journal deadline survive worker relaunches
while the service journal and device identity stay the same; a mount with a
different device identity gets a separate episode. The first low observation
persists the start time, the 10-minute degraded deadline (D), the later
5-minute drain deadline (E = D + 5 minutes), and the episode's one reclaim
claim. Relaunches reuse both deadlines and do not claim another reclaim. The
claim is at-most-once: a crash after it commits but before cleanup can skip
that physical attempt, but cannot reset the deadlines or admit work. Clock
rollback or a filesystem identity change also fails closed.

While any pressure episode is active, the worker refuses job admission. The
controller treats active or unmeasurable pressure as unavailable: it stops
idle waiter children and withholds permit grants and recovery. At D, a still
low observation enters `Drain`; the worker accepts no new jobs, waits up to
60 seconds, then rechecks the persisted episode and filesystem. Terminal is
latched only when a still-low observation arrives at or after E. `Deregister`
then runs failed-slot cleanup, deleting the registration and clearing local
slot state.

At terminal pressure, the controller revokes pressure launch leases and fences
desired slot generations. It clears a terminal episode only after every
configured root has a fresh healthy measurement, every desired slot is
Fenced, no jobs remain active, and a compare-and-swap matches the episode ID
and revision. Fenced slots resume through the next-generation path. A
nonterminal episode can recover on healthy measurements without terminal slot
fencing. Clock rollback and filesystem identity changes are fail-closed
exceptions to the D/E timeline.

Admission is evaluated *before* a job is acquired, so a slot does not claim a
job when any checked filesystem cannot support admission.

File-store reclaim is bounded: it coordinates concurrent reclaim, targets a
byte goal, skips candidates covered by live leases, and reports what it freed.
The emergency path can remove eligible Velnor file-store entries, reclaim
orphaned UUID workspaces on the pressured filesystem when Docker-backend
liveness checks are available, and consider BuildKit pruning only if a fresh
free-space sample after file-store reclaim remains below 2 GiB. Pruning
requires an unclaimed current-domain builder and stops its daemon. It does not
prune dangling images or delete the BuildKit builder or state volume. It does
not scrub bytes.

`velnorctl storage paths` lists the configured cache, library, run, and log
roots. `velnorctl storage status` recursively sizes direct class directories
under each keyed trust namespace derived as a sibling of the cache root,
including `git-mirrors`, and separately sizes the canonical host-global
`gha-cache` root in full, including tenant data and stable lock metadata. For
`gha-cache`, `velnorctl cache du` reports the tenant subtree and GC evaluates
tenant directories as candidates, so neither covers root-level stable lock
metadata. `storage status` omits the shared artifact root, Docker/BuildKit,
and per-slot stable workspaces. `velnorctl cache du` sizes artifacts,
Git-mirror roots, per-slot stable-workspace roots, and the tenant subtree of
the canonical host-global `gha-cache` root; it also reports Docker usage
separately when measurable. Stable-workspace roots appear in `cache du` but
are excluded from ordinary `cache gc`; disk-pressure reclaim may consider an
idle, unleased workspace only when its separate pressure and filesystem gates
pass.
`velnorctl storage explain-pressure` is not available.
