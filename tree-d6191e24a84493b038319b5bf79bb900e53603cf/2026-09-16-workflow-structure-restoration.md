# Workflow structure restoration — analysis and design draft

Status: **approved direction** (pre-implementation). See **§13 Final recommendation**.  
Scope: GitHub Actions surface generated by `velnor-workflow` for `tailrocks/velnor`.  
**Master plan:** [`2026-09-16-ci-master-plan.md`](2026-09-16-ci-master-plan.md) (unified workflow + cache delivery).  
Related: PR [#867](https://github.com/tailrocks/velnor/pull/867) (both-lane contract), generic workflow generator migration (`6e59b98d`).

---

## 1. Problem statement

After the recent workflow refactoring, CI is hard to read in GitHub:

- It is unclear **which crate/unit** is building, testing, or failing.
- The overall graph feels **flat, duplicated, and noisy** compared to the pre-refactor layout.
- PR #867 improved **lane visibility** (GitHub vs Velnor) but did so by reshaping the hierarchy in a way that **obscures unit identity** at the top level.

We need a target structure that satisfies both:

1. **Unit-first readability** — a developer scanning Checks or the Actions sidebar can immediately see `velnor-runner`, `velnor-workflow`, `docker`, etc.
2. **Lane clarity** — each check name must unambiguously state whether it ran on **GitHub-hosted** or **Velnor** capacity (and control-plane jobs must stay distinguishable).

This document analyzes what changed, why it broke UX, what GitHub forces us to respect, and a recommended direction before we lock the final generator design.

## 2. Timeline — three structural eras

### Era A — per-unit reusable workflows (pre `6e59b98d`, ~Sep 2025)

**Shape**

| Layer | Example |
|---|---|
| Aggregate caller (1 per unit) | `Rust · velnor-runner` |
| Reusable workflow file (1 per unit) | `ci-rust-velnor-runner.yml` |
| Inner lane jobs | `GitHub`, `Velnor` |

**GitHub Checks names**

```
Rust · velnor-runner / GitHub
Rust · velnor-runner / Velnor
```

**What worked**

- Crate/unit identity at the **top level** of the check tree.
- Lane visible as the **inner** job name.
- Sidebar matched mental model: one row per crate, expand to see lanes.

**What did not work**

- Lane token alone (`GitHub` / `Velnor`) is ambiguous when many units run in parallel — you must read the parent to know the crate.
- One workflow **file** per unit → repository growth and generator maintenance cost.
- Selection traveled via **artifacts** (`selection-artifact`), adding latency and failure modes.

**Scale (this repo)**

- ~20 aggregate callers, ~20 reusable workflow files.
- Well under GitHub’s 50 unique reusable-workflow **file** limit per caller workflow.

---

### Era B — per-kind reusable, single kind caller (post rearchitecture, pre #867)

**Shape**

| Layer | Example |
|---|---|
| Aggregate caller (1 per kind) | `Rust` |
| Reusable workflow file (1 per kind) | `ci-unit-rust.yml` |
| Inner lane+unit jobs | `GitHub / rust-velnor-runner`, `Velnor / rust-velnor-runner` |

**GitHub Checks names**

```
Rust / GitHub / rust-velnor-runner
Rust / Velnor / rust-velnor-runner
```

**What worked**

- Consolidated to **one reusable file per kind** → solves file-count growth and enables sharding for the 500 KiB limit.
- Selection passed via **inputs** (no selection artifact).
- Still possible to see unit id at the leaf.

**What did not work**

- Kind-first grouping hides crates until you expand `Rust`.
- Lane buried in the **middle** segment (`Rust / GitHub / …`) — the original motivation for #867.
- `ci-unit-rust.yml` already ~5.8k lines with full github+velnor duplication per unit.

---

### Era C — lane-split callers (#867, current `main`)

**Shape**

| Layer | Example |
|---|---|
| Aggregate callers (3 per Rust kind) | `GitHub / Rust`, `Velnor / Rust`, `Control / Rust` |
| Reusable workflow file (still 1 per kind) | `ci-unit-rust.yml` |
| Inner unit jobs | `rust-velnor-runner` (bare unit id) |
| Control prep | `prepare-cargo` under `Control / Rust` |

**GitHub Checks names**

```
GitHub / Rust / rust-velnor-runner
Velnor / Rust / rust-velnor-runner
Control / Rust / prepare-cargo
```

**What worked**

- Lane is the **first** token in the check name — #867’s explicit goal.
- Strict **both-lane contract**: generation fails if a unit cannot pair; fork PR admission gate; `lane_compare --strict`.
- Callers dropped from 20 files to **3 reusable calls per kind** (plus control).

**What broke UX**

- **Unit identity moved to the leaf** and lost human labels (`Rust · velnor-runner` → `rust-velnor-runner`).
- Checks list is grouped by **lane first**, so parallel PR CI reads as three large Rust buckets instead of fifteen crate rows.
- **6377 lines** in `ci-unit-rust.yml`; ~15k lines total under `.github/workflows/`.
- Near-complete **duplication** of github and velnor job bodies (setup, cache, timing markers repeated per unit per lane).
- Extra control dimension (`Control / Rust`) is correct architecturally but adds a third top-level group users must understand.

## 3. Symptom → root cause map

| Symptom | Root cause | Introduced |
|---|---|---|
| Cannot see which crate is building at a glance | Aggregate groups by **kind/lane**, not **unit** | Era B (#867 amplified) |
| Checks feel duplicated / noisy | Full job bodies emitted per `(unit × lane)` inside one YAML file | Era B, grew in C |
| `rust-velnor-runner` instead of `Rust · velnor-runner` | Inner jobs forced to bare `unit.id` so caller supplies lane prefix | Era C (#867) |
| Three Rust groups in sidebar | Lane-split callers (`group-rust-github`, `-velnor`, `-control`) | Era C (#867) |
| Massive generated YAML | Kind-monolith + no step deduplication via composite actions | Era B |
| Hard to compare lanes for one crate | Lane-first grouping separates GitHub and Velnor checks into different subtrees | Era C |

Architecturally, #867 solved **naming for lane_compare** but chose **lane-first aggregation**, which conflicts with **unit-first operator mental model**. The deeper regression started in Era B when **callers collapsed from per-unit to per-kind**.

## 4. GitHub platform constraints (non-negotiable)

The generator already encodes these; any redesign must preserve them.

| Constraint | Limit | Current mitigation |
|---|---|---|
| Unique reusable workflow **files** referenced by one workflow | 50 | One file per kind (`ci-unit-rust.yml`), not one per unit |
| Workflow file size | 500 KiB | Shard kind files at ~480 KiB (`ci-unit-rust-2.yml`) |
| Reusable nesting and Checks naming | Caller `name` + inner job `name` | Deliberate split of lane vs unit tokens |
| Matrix over units | Skipped jobs still clutter UI; hard to gate per unit | Linear jobs filtered by `selected_units` input |
| Same-repo pinned reusable on push/schedule | Scheduling wedge | Policy forbids; aggregate uses unpinned `./.github/workflows/...` |

**Important distinction:** GitHub counts **unique workflow files**, not **call count**. Era A used ~20 calls to ~20 files. We can use ~18 calls to **one** `ci-unit-rust.yml` — the consolidation win of Era B is kept even if callers return to per-unit.

**Scale check (this repo today):** 18 verification units (13 Rust + 5 other kinds). Per-unit callers → ~18 unique reusable files if we revert files, or ~5 files with ~18 calls if we keep kind files. Both are under 50.

## 5. Design requirements

### Must have

1. **Unit-first Checks hierarchy** — top-level group identifies the verification unit (crate, docker image, docs, etc.).
2. **Lane suffix when multi-lane** — when `runners = both`, append `(GitHub)` or `(Velnor)` to the unit name; when only one lane is configured, use the bare unit name with no suffix. Applies to **every unit kind** (Rust, Bun, Docker, Docs, OpenTofu) — one generic rule, no kind-specific naming exceptions.
3. **Both-lane contract** — retain #867 invariants: paired lanes, no silent single-lane degrade, fork admission, strict compare tooling.
4. **Affected selection** — plan job chooses units; unselected units skip cleanly.
5. **Generator-owned surface** — no hand-edits under `.github/`; changes go through `velnor-workflow` + regen.
6. **Stay within GitHub limits** — ≤50 reusable files per aggregate; shard kind workflows by bytes.

### Should have

7. **Human-readable labels** — restore `sidebar_group_name` pattern: `Rust · velnor-runner`, not bare ids.
8. **Reduced YAML duplication** — shared setup via composite actions or centralized templates (runtime download, selection materialize, toolchain, timing).
9. **Stable names for branch protection / rulesets** — `Control / Required`, `Policy`, etc. stay compatible or migrate with an explicit ruleset update plan.
10. **Deterministic regen** — byte-stable output for unchanged inputs.

### Nice to have

11. **Runner identity in Velnor checks** — keep `Velnor runner identity` step output for debugging host/slot.
12. **Phase timing reports** — keep existing timing markers where they aid perf work.

## 6. Options considered

### Option 1 — Revert to Era A literally (per-unit workflow files)

Restore `ci-rust-{unit}.yml` for every scanned unit.

| Pros | Cons |
|---|---|
| Best historical UX | File count grows with monorepo; sharding story harder |
| Simple inner jobs (`GitHub` / `Velnor`) | Duplication across files unless heavily templated |
| Proven in this repo | Loses kind-level byte sharding centralization |

**Verdict:** Good UX reference, but file proliferation fights monorepo scale unless paired with aggressive templating.

---

### Option 2 — Keep Era C (#867) and polish labels only

Rename inner jobs to `Rust · velnor-runner` while keeping lane-split callers.

| Pros | Cons |
|---|---|
| Minimal generator churn | Still lane-first grouping — crate visibility problem remains |
| Keeps lane_compare patterns | Longer inner names; duplicates kind prefix |

**Verdict:** Insufficient — does not fix the primary readability regression.

---

### Option 3 — **Recommended:** Unit-first flat names + kind reusable files

Combine Era A’s **unit-first mental model** with Era B’s **single kind reusable file**. Lane is expressed as a **parenthetical suffix on the unit name**, not as a separate hierarchy segment.

**Target check names**

When `runners = both` (this repository today):

```
Rust · velnor-runner (GitHub)
Rust · velnor-runner (Velnor)
Bun · velnor (GitHub)
Bun · velnor (Velnor)
Docker · Docker (GitHub)
Docker · Docker (Velnor)
Documentation · Documentation (GitHub)
Documentation · Documentation (Velnor)
OpenTofu · OpenTofu (GitHub)
OpenTofu · OpenTofu (Velnor)
Control / Planning
Control / Prepare Cargo        ← Rust-only shared prep
Control / Aggregate
Control / Required
```

When `runners = github` or `runners = velnor` (single lane):

```
Rust · velnor-runner
Bun · velnor
Docker · Docker
Documentation · Documentation
OpenTofu · OpenTofu
```

No `(GitHub)` / `(Velnor)` suffix when only one lane exists — the lane is implicit from configuration. The `{kind} · {unit label}` prefix comes from `sidebar_group_name(unit)` for every kind; only the Rust control prep job is kind-specific.

**Naming helper (generator)**

```rust
/// Display name for a verification job in the Checks UI.
fn unit_job_display_name(unit: &Unit, lane: Option<RunnerMode>, runners: RunnerMode) -> String {
    let base = sidebar_group_name(unit); // e.g. "Rust · velnor-runner"
    match runners {
        RunnerMode::Both => format!(
            "{} ({})",
            base,
            lane.expect("both mode requires explicit lane per job").display_name()
        ),
        RunnerMode::Github | RunnerMode::Velnor => base,
    }
}
```

**Aggregate (`ci-pr.yml`, `ci-main.yml`, `nightly.yml`)**

When `runners = both`, one reusable caller **per (unit, lane)** — flat name on the caller, no lane split by kind:

```yaml
group-unit-rust-velnor-runner-github:
  name: "Rust · velnor-runner (GitHub)"
  if: ... unit selected ...
  needs: [plan, policy]
  uses: ./.github/workflows/ci-unit-rust.yml
  with:
    unit: rust-velnor-runner
    lane: github
    selected_units: ${{ needs.plan.outputs.units }}
    scope: ...
    base_sha: ...
    head_sha: ...

group-unit-rust-velnor-runner-velnor:
  name: "Rust · velnor-runner (Velnor)"
  needs: [plan, policy, group-rust-control]   # after shared prep if any
  uses: ./.github/workflows/ci-unit-rust.yml
  with:
    unit: rust-velnor-runner
    lane: velnor
    ...
```

When `runners = github` only, one caller per unit with the bare name:

```yaml
group-unit-rust-velnor-runner:
  name: "Rust · velnor-runner"
  uses: ./.github/workflows/ci-unit-rust.yml
  with:
    unit: rust-velnor-runner
    lane: github
    ...
```

**Kind reusables (`ci-unit-rust.yml`, `ci-unit-bun.yml`, `ci-unit-docker.yml`, `ci-unit-docs.yml`, `ci-unit-opentofu.yml`)**

Same contract for every kind file:

- Accept `unit` + `lane` inputs; emit **one job** for that pair (not all units × all lanes in one call).
- Job `name:` = same string as the caller (or omit inner `name:` and rely on caller — see nesting note below).
- Keep `selected_units` gating so skipping stays explicit.

Rust-only exception: when `lane: control`, `ci-unit-rust.yml` emits `prepare-cargo` under **`Control / Prepare Cargo`**. This job warms the shared Velnor Cargo store (`cargo fetch --locked`) so subsequent Velnor Rust jobs can run with `CARGO_NET_OFFLINE=true`. No equivalent exists for Bun/Docker/Docs/OpenTofu.

**Reusable nesting note**

GitHub composes reusable check names as `{caller name} / {called job name}`. To keep the UI close to the flat target:

- Prefer **one job per reusable invocation** with no inner `name:` override (or a generic inner name like `verify` only if the UI collapses it).
- Longer term: move shared steps into **composite actions** so comparison jobs can live inline in the aggregate with zero nesting. WP4 tracks this.

**Both-lane contract**

- Generation still requires a github+velnor job pair per unit when `runners = both`.
- `lane_compare --strict` pattern becomes `{sidebar_group_name} ({GitHub|Velnor})` — update golden patterns in `velnor-tools`, not drop the contract.

| Pros | Cons |
|---|---|
| Unit and lane in one readable string | ~2× aggregate callers when `both` (~36 vs ~18 units) |
| No lane-first grouping | Must verify reusable nesting does not re-introduce `/` prefixes |
| Single-lane repos stay clean (no suffix) | Requires `unit` + `lane` inputs + generator changes |
| Keeps 1 reusable file per kind | Must update tests (`lane_pairing.rs`, `velnor_first_ci.rs`) |

## 7. Recommended target architecture

```
┌─────────────────────────────────────────────────────────────┐
│  CI / PR  (aggregate workflow)                              │
│  ├─ Control / Planning                                      │
│  ├─ Policy                                                  │
│  ├─ Control / Velnor admission (fork guard)                   │
│  ├─ Rust · velnor-runner (GitHub)  ──► ci-unit-rust.yml     │
│  ├─ Rust · velnor-runner (Velnor)   ──► ci-unit-rust.yml     │
│  ├─ Rust · velnor-workflow (GitHub)                         │
│  ├─ Rust · velnor-workflow (Velnor)                         │
│  ├─ Bun · velnor (GitHub)        ──► ci-unit-bun.yml        │
│  ├─ Docker · Docker (Velnor)     ──► ci-unit-docker.yml     │
│  ├─ … (one row per unit × lane when both, every kind)       │
│  ├─ Control / Prepare Cargo (Rust-only shared prep)       │
│  ├─ Control / Aggregate                                     │
│  └─ Control / Required                                      │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  ci-unit-rust.yml  (kind reusable, sharded if >480 KiB)     │
│  when unit=rust-velnor-runner, lane=github:                 │
│    └─ one job  (runs-on: ubuntu-24.04)                      │
│  when unit=rust-velnor-runner, lane=velnor:                   │
│    └─ one job  (runs-on: [self-hosted, …])                  │
└─────────────────────────────────────────────────────────────┘
```

When `runners = github` or `runners = velnor`, the aggregate lists `Rust · velnor-runner` (no suffix) instead of the `(GitHub)` / `(Velnor)` pair.

### Naming contract (canonical)

| Job role | `name:` pattern | Example check (both lanes) | Example check (single lane) |
|---|---|---|---|
| Plan | `Control / Planning` | `Control / Planning` | same |
| Unit verification | `unit_job_display_name(unit, lane, runners)` | `Rust · velnor-runner (GitHub)`, `Docker · Docker (Velnor)`, … | `Rust · velnor-runner`, `Docker · Docker`, … |
| Shared prep | `Control / Prepare Cargo` | `Control / Prepare Cargo` | same |
| Aggregate gate | `Control / Aggregate` | … | … |
| Branch protection mirror | `Control / Required` | `CI / Required` | same |

Rules:

- **`runners = both`** → every comparison job includes `(GitHub)` or `(Velnor)`.
- **`runners = github`** or **`runners = velnor`** → comparison jobs use bare `{sidebar_group_name}`; lane is implicit.
- **Control plane** jobs keep the `Control / …` prefix regardless of runner mode.

Use existing helpers:

- `sidebar_group_name(unit)` → `Rust · velnor-runner`
- `unit_display_label(unit)` for humanized crate names
- `control_job_name(label)` for control plane
- **New:** `unit_job_display_name(unit, lane, runners)` as above

Drop the #867 rule that inner comparison jobs must equal bare `unit.id`.

### YAML size reduction (parallel track)

Even with restored hierarchy, shrink the monolith:

1. **Composite action** for repeated blocks: runtime artifact download+verify, selection materialize, timing markers, rust toolchain restore.
2. **Lane-specific composites** only where backends diverge (mbx backend, cache keys).
3. Re-measure shard boundaries after extraction — goal is keep `ci-unit-rust.yml` single-shard for this repo’s current unit count.

## 12. Summary recommendation

**Do not revert the both-lane contract from #867** — it fixed real pairing and admission bugs.

**Do revert the lane-first aggregation model from #867** — it traded away unit visibility.

The sweet spot is **Option 3**: **unit-first flat names** (Era A UX) + **kind reusable files** (Era B scale) + **parenthetical lane suffix when both** + **shared control prep** (one place, not per lane).

That gives check names like `Rust · velnor-runner (Velnor)` or `Docker · Docker (GitHub)` when both lanes are active, and bare `sidebar_group_name` when only one lane is configured — *what* and *where* in one string, uniformly across all unit kinds, without a lane-first hierarchy.

## 13. Final recommendation (sponsor review, 2026-09-16)

**Verdict: GO — implement Option 3 in three PRs.**

### What we are fixing

Era C (#867) made lane visible but hid crates behind `GitHub / Rust / rust-velnor-runner`. We restore **unit-first** names: `Rust · velnor-runner (GitHub)`, keep the both-lane contract, and keep `Control / Prepare Cargo`.

### The one structural insight

Per-(unit,lane) aggregate callers means **each `workflow_call` runs one job in isolation**. Two things follow:

1. **Dependency-closure** (`velnor_rust_needs = dependency-closure`) must move from inner `ci-unit-rust.yml` `needs:` to **aggregate caller `needs:`**. Example: `Rust · velnor-client (Velnor)` waits for `Rust · velnor-model (Velnor)` at the aggregate level.
2. **Check names** with reusables are always `{caller} / {inner}`. Truly flat names (no `/`) require inline aggregate jobs + composite actions (PR3). PR1 accepts `Rust · velnor-runner (GitHub) / verify` — still a major UX win.

### Delivery plan

| PR | Scope | Ships |
|---|---|---|
| **PR1** | CI structure + naming + dependency lift + `lane_compare` + tests + regen | `ci-pr`, `ci-main`, `nightly`, `ci-unit-*`, **`release.yml` unit verify names** |
| **PR2** | Operator docs + fleet grep for stale dashboards | `execution.mdx`, changelog |
| **PR3** | Composite extraction (YAML size + optional flat names) | `.github/actions/velnor-ci-*` |

### PR1 generator checklist

1. Add `unit_job_display_name()` in `lib.rs`.
2. Replace `kind_reusable_callers()` with per-(unit,lane) callers in `render_node_callers()`.
3. Add `unit` input to kind reusables; one inner job keyed `verify`, **omit inner `name:`**.
4. Rename prep caller to `Control / Prepare Cargo`; Velnor Rust callers `needs` it.
5. Lift `velnor_rust_dependency_needs()` to aggregate caller ids (`group-unit-rust-velnor-model-velnor`, etc.).
6. Regenerate `render_nodes_required()` for ~37 caller ids.
7. Rewrite `lane_compare` for `(GitHub)` / `(Velnor)` suffix parsing.
8. Rewrite tests: `lane_pairing.rs`, `velnor_first_ci.rs`, `synthetic_surface.rs`, shard tests.
9. One line in `release.rs`: `comparison_job_name` → `unit_job_display_name`.

### Cache-safe requirements (PR1)

Restoration must **not change cache keys** for unchanged units. Keys are keyed on `unit.id` + scanned `CacheSpec`, not caller display names.

1. Preserve mbx keys: `velnor-mbx-v3-{digest}-…-{unit.id}-…`
2. Preserve actions/cache keys: `ci-${{ runner.os }}-rust-${{ hashFiles(key_files) }}`
3. Lift dependency-closure to aggregate `needs:` — required for Velnor host-persistent Cargo ordering
4. Keep single `Control / Prepare Cargo` before Velnor Rust callers
5. PR3 composites: restore/save/`cache-hit` gates must stay in **one job** (never split across jobs)
6. Add golden test: regen does not change cache keys or `hashFiles(...)` args per unit

See **[2026-09-16-cache-reuse-and-retention-plan.md](2026-09-16-cache-reuse-and-retention-plan.md)** for the full cache work packages (WP-C0–C6) and **Appendix D** for inventory summary.

### Do not

## Appendix D — cache architecture verification (2026-09-16)

### GitHub lane — cache layers per Rust job

| Layer | Mechanism | Save on PR? | Save on main push? |
|---|---|---|---|
| Cargo registry/git | `actions/cache` | Restore only | Save (if not exact hit) |
| Mr. Boxington compile | `mr-boxington-action` objects v1.8.3 | Restore only | Save via action |
| Rust toolchain | `actions/cache` on `~/.rustup` | Restore only | Save |
| mold linker | `actions/cache` | Restore only | Save |
| Mise tools | `mise-action cache: true` | Restore (+ may save) | Save |

**Trusted save gate** (all `actions/cache/save` steps): `push@main || schedule || workflow_dispatch@main`. PR and merge_group **restore but never save** — by design.

### Velnor lane

Host-persistent mounts (`~/.cargo/registry`, `~/.cargo/git`, mbx local, mise) — no GHA cache I/O. `Control / Prepare Cargo` warms shared store before parallel Rust jobs. `CARGO_NET_OFFLINE` on checks; network allowed only during fetch.

### Docker (GitHub)

Restore `.velnor-docker-cache` seed on every run. PR builds `--target ci` only (no export/save). Full build + seed save on main/nightly only.

### Known gaps (pre-existing, not caused by restoration)

| Gap | Impact | Mitigation |
|---|---|---|
| PR never writes cache | PR depends on prior main/nightly saves | Expected; main push after merge warms cache |
| merge_group not in save gate | Merge queue runs full build but does not persist seed/mbx/cargo saves | Consider adding merge_group to trusted gate (separate change) |
| Source change on PR | mbx freshness hash miss → prefix fallback (partial warm) | Expected; exact key updates on next main save |
| rust-policy mbx freshness = all `**/*.rs` | Any Rust edit invalidates policy compile cache | Broad by design |
| merge SHA ≠ PR head caches | Documented BLOCKED in fleet evidence §9.2 | merge_group uses different SHA than PR |

### Restoration impact on cache

**Neutral** if: cache steps still rendered per `inputs.unit`, keys use `unit.id`, dependency closure + prep ordering preserved. **Regression risk:** wrong aggregate `needs:` → Velnor cold/offline failures (ordering, not key miss).
